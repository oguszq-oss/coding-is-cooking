# 餐厅类比手册：用一家餐厅理解常见技术术语

> 用途：让完全不懂编程的人（比如一位餐厅服务员），也能理解每个编程术语"是做什么的"。
> 方法：把软件世界暂时映射成一家餐厅。遇到生词，先问四个问题——**它解决什么问题？谁在什么时候执行？输入输出往哪走？哪条技术边界不能被比喻吃掉？** 餐厅画面只能帮助建立直觉，不能反过来定义技术。
> 与正式资料的关系：本手册只管“第一印象”。需要据此做安全、架构、成本或产品判断时，再查项目文档和官方一手资料；类比不是证据。

# 〇、总设定：整个软件就是一家餐厅

## 核心映射总表（先认清角色与方向，其他概念再按场景展开）

| 编程概念                 | 餐厅类比                   | 一句话说透                                       |
| ------------------------ | -------------------------- | ------------------------------------------------ |
| 一个软件产品             | 一家餐厅                   | 食客（用户）来消费，前厅招待，后厨做菜           |
| 用户                     | 食客                       | 提出需求并使用结果；现实系统还会保存用户资料     |
| 前端                     | 前厅与点餐界面             | 接住操作并呈现结果，也可能在用户设备上运行       |
| 后端                     | 后厨业务工位               | 在服务端执行业务规则并返回结果                   |
| 数据库                   | 冷库 / 账本 / 档案柜       | 按数据内容选物件：食材说冷库，记录说账本或档案柜 |
| API（接口）              | 正式通道 + 通道规矩        | 包含地址、操作、输入、输出和错误约定，不只是一扇窗口 |
| 软件开发                 | 设计并搭起整套餐厅服务     | 写代码只是其中一环，还包括测试、发布与维护       |
| 编程语言                 | 菜系 / 厨艺流派            | 川菜、粤菜、淮扬菜——都是做菜，章法完全不同     |
| 框架                     | 一套操作规程与现成设施     | 规定常见结构并提供可复用能力，不是质量等级       |
| 大模型                   | 负责判断的厨师长           | 只取“按交代和材料生成内容”这一点，不赋予人的责任 |
| IDE / 编程工具           | 工作台与工具柜             | 帮开发者阅读、编辑、运行和检查代码               |
| Harness                  | 厨房的布局、动线与规章制度 | 厨师总在同一个地方出错，该改的是厨房，不是换厨师 |
| 上线部署                 | 开业迎客                   | 从试菜到正式开门                                 |

## 为什么这个类比成立

餐厅和软件有同构的"三层 + 通道"结构：

- **食客主要接触前厅** ↔ 用户通常通过页面或客户端操作系统；
- **前后厅职责不同** ↔ 前端负责交互与呈现，服务端负责受信任的业务处理；边界会因架构变化；
- **前后厅按正式规矩传递要求和结果** ↔ 客户端与服务端按 API 契约交换请求和响应；API 不保证只有一种传输方式；
- **食材与账目都要妥善保存** ↔ 不同数据需要合适的存储、备份和访问控制；
- **饭点会挤爆、厨师会出错、新菜要试卖** ↔ 系统有高并发、有 bug、要灰度发布。

> 对最初设想的微调：原设想里"Python、Java = 不同的锅铲"。本手册改为"菜系/厨艺流派"——因为语言决定的是**做菜的章法和思维方式**（同样是鱼，川菜水煮、粤菜清蒸），而锅铲只是工具，更接近 IDE。这样整个体系里"工具（锅具）= IDE、厨艺（大脑）= 大模型、章法（菜系）= 编程语言"各归其位，不会互相打架。

# 一、前厅篇

> 场景故事：一位食客推门进店——他看到的装修、坐下的桌椅、递上的菜单、服务员的应答、桌上的叫号屏……这一切就是"前端"。食客永远不会进后厨，他对这家店的全部印象都由前厅决定。

## 1. 前厅的硬装与软装（网页基础）

| 术语        | 餐厅类比                   | 一句话说透                                                         |
| ----------- | -------------------------- | ------------------------------------------------------------------ |
| HTML        | 前厅的空间结构             | 哪里是门、哪里是吧台、摆几张桌子——只管"有什么"，不管好不好看     |
| CSS         | 装修与摆盘                 | 灯光、桌布、餐具摆放、上菜的卖相——90% 的"改好看点"都改在这层     |
| JavaScript  | 前厅会动的机关             | 点餐铃、叫号屏、自动门——一切"有反应"的东西背后都是它             |
| TypeScript  | 开门前核对程序用法         | 静态检查主要发生在运行前；真实网络输入仍要运行时校验               |
| 浏览器      | 食客手里的点餐终端         | 读取并运行 Web 资源；不同实现与版本会带来兼容性差异                |
| WebAssembly | 前厅能执行的另一种指令格式 | 让编译后的模块在 Web 平台运行，不等于把后端或某种语言整体搬进前端 |

## 2. 服务流派（框架层）

> 前端框架或 UI 库可以先记成**组织服务单元的章法**。它们的抽象、编译和运行模型不同；品牌气质、地域偏好和流行度会变化，不写成餐厅档次排行榜。

| 术语    | 餐厅类比             | 一句话说透                                                       |
| ------- | -------------------- | ---------------------------------------------------------------- |
| React   | 可组合的服务单元工具箱 | 用组件描述 UI；严格说是 UI 库，路由等能力通常另行组合             |
| Vue     | 渐进式服务章程         | 可逐步采用，围绕声明式渲染和组件组织界面                          |
| Angular | 总部成套运营体系       | 提供较完整的框架能力与明确约定，不只适用于“大企业”                |
| Svelte  | 开门前多做编排的体系   | 编译阶段承担较多转换工作，减少部分浏览器运行时框架工作             |
| SolidJS | 只通知受影响桌位的体系 | 采用细粒度响应更新；不能仅凭这一点断言所有项目都更快               |
| Qwik    | 封存现场、按需恢复服务 | 强调 resumability 与按需加载；实际体验仍取决于应用与部署           |

## 3. 统一采购的餐具与服务包（组件库）

> 组件库 = 统一采购的**成套餐具 + 标准服务包**。自己烧瓷打碗又贵又不统一，直接整套买——"先声明用哪套餐具，AI 就不会自己手搓碗筷。"

| 术语         | 餐厅类比           | 一句话说透                                 |
| ------------ | ------------------ | ------------------------------------------ |
| Ant Design   | 企业产品组件套装   | 提供设计规范和大量现成组件；是否合适取决于产品与定制需求 |
| Element Plus | Vue 3 组件套装     | 面向 Vue 3 的组件库，中文资料较易获取                       |
| Material UI  | Material 风格套装  | React 生态中的 Material Design 组件实现                    |
| Arco Design  | 企业级设计套装     | 提供组件、设计资源与多语言资料                              |
| Naive UI     | Vue 3 组件套装     | 以 Vue 3 与 TypeScript 为基础，支持主题配置                 |
| Chakra UI    | 可组合组件套装     | 注重可组合 API 与无障碍基础；成品仍需实际做无障碍验收       |

## 4. 连锁加盟的开店手册（应用框架）

> 应用框架 = **加盟总部给的一整本开店手册**：装修图纸、动线设计、员工培训、开业流程全写好，照着做就能开出一家像样的店。

| 术语           | 餐厅类比                      | 一句话说透                                           |
| -------------- | ----------------------------- | ---------------------------------------------------- |
| Next.js        | React 项目开店手册             | 提供路由、渲染、数据获取和构建约定；有 SEO 能力不等于保证排名 |
| Nuxt           | Vue 项目开店手册               | 为 Vue 应用提供路由、渲染与服务端等整套约定                  |
| SvelteKit      | Svelte 项目开店手册            | 为 Svelte 应用提供路由、渲染和构建部署约定                    |
| Ant Design Pro | 后台管理样板房与脚手架         | 面向中后台场景的方案，不与前三者视作同类全栈应用框架          |

## 5. 开业前的备料流水线（构建层）

> 构建工具 = **开业前的备料备餐流水线**：把毛菜（源代码）洗切配、预处理成净菜包（浏览器能直接加载的文件）。普通沟通只需知道自家店用哪条流水线，出问题时把名字报给"厨师"。

| 术语    | 餐厅类比               | 一句话说透                                   |
| ------- | ---------------------- | -------------------------------------------- |
| Vite    | 快速开发与构建备料线   | 强调现代开发服务器体验，也提供生产构建能力              |
| Webpack | 高度可配置的模块流水线 | 生态成熟；速度和复杂度取决于版本、配置与项目             |
| Rollup  | 模块打包流水线         | 常用于库的构建，也可用于应用；不保证产物天然更小         |
| Rspack  | 重视兼容的高速流水线   | 以 Rust 实现并重视 Webpack 生态兼容；迁移成本不能说近乎零 |

## 6. 运行时与包管理（转换层）

> 这一层食客完全感知不到，但没有它餐厅一天都开不了张。

| 术语    | 餐厅类比       | 一句话说透                                                               |
| ------- | -------------- | ------------------------------------------------------------------------ |
| Node.js | 浏览器外的 JavaScript 工作台 | JavaScript 运行时，可用于服务端和开发工具；不是水电或编程语言本身          |
| npm     | 采购部（默认） | 拿着供应商名录去批发市场订食材（依赖包）的那个部门                       |
| pnpm    | 精明的采购部   | 订得快、仓库占用省，管多家分店时尤其好用                                 |
| Yarn    | 老牌采购部     | 早年解决了默认采购部又慢又乱的问题，老店常见                             |
| Bun     | 运行时与工具链套装     | 同时提供 JavaScript 运行时、包管理、测试和构建等能力；兼容性要按项目验证   |

## 7. 外卖与餐车（延伸领域 · 移动端）

> 做手机 App = 餐厅不满足于堂食，开始做**外卖和餐车业务**。

| 术语         | 餐厅类比           | 一句话说透                                               |
| ------------ | ------------------ | -------------------------------------------------------- |
| React Native | 用 React 章法做原生餐车 | 用 React 模型构建原生应用，可共享部分业务知识但不是网页原样搬过去 |
| Flutter      | 自带渲染体系的多平台车队 | 用 Dart 与自己的渲染体系构建多平台应用，仍需处理各平台差异       |
| Swift        | Apple 平台常用菜系       | 常用于 Apple 平台开发，也是一门通用编程语言                     |
| Kotlin       | Android 常用菜系          | 广泛用于 Android，也可用于服务端和多平台等场景                   |

## 8. 前厅的共享信息（状态管理）

> 状态管理可以先记成前厅的**共享白板**：哪些信息只归当前桌，哪些需要多个岗位共同读取，怎样更新才不互相覆盖。规模不是唯一判断标准；简单页面也可能不用专门状态库，大应用也会组合多种状态方式。

| 术语    | 餐厅类比             | 一句话说透                                         |
| ------- | -------------------- | -------------------------------------------------- |
| Redux   | 可预测的集中看板制度 | 围绕明确的数据流组织状态；是否需要取决于应用复杂度与团队约定 |
| Pinia   | Vue 生态共享白板     | Vue 生态推荐的状态管理方案，API 相对精简                   |
| Zustand | 轻量状态小看板       | React 生态中的轻量状态库，不等于只适合中小项目             |
| Vuex    | 既有 Vue 项目的白板  | 仍见于既有项目；新项目通常会同时评估 Pinia                 |

## 9. 传菜员的装备（数据请求）

> 数据请求 = 传菜员的**对讲机和点单 Pad**——前厅找后厨要菜全靠它。

| 术语        | 餐厅类比       | 一句话说透                                                 |
| ----------- | -------------- | ---------------------------------------------------------- |
| Axios       | 请求工具       | 封装 HTTP 客户端能力；原生 `fetch` 也很常用，不写成唯一标配 |
| SWR         | 缓存后再核实的联络簿 | 围绕 stale-while-revalidate 管理远端数据，行为由配置决定   |
| TanStack Query（React Query） | 服务端状态工作台 | 管理异步数据的获取、缓存、同步与更新，不只是“更高级的 Axios” |

## 10. 前厅杂项

| 术语         | 餐厅类比                 | 一句话说透                                                                           |
| ------------ | ------------------------ | ------------------------------------------------------------------------------------ |
| Tailwind CSS | 原子化装修词库           | 用 utility class 组合样式；仍需设计规则，不等于不写 CSS 或天然更好看                  |
| Three.js     | 前厅的全息投影 / 3D 表演 | 产品 3D 展示、炫酷特效，镇店噱头                                                     |
| 组件         | 可组合的服务单元         | 封装结构、样式和行为；复用实例不会自动让所有已部署页面同步改变                       |
| 路由         | 前厅分区图               | 靠窗区、包厢区、吧台区——报位置（URL）就知道去哪个区域；"404"就是"您要的位置不存在" |
| 依赖         | 外购食材与设备           | 不是自己种的养的，全记进货单（package.json）上；"加依赖" = 引入新供应商              |
| 构建打包     | 打烊备餐                 | 把今晚的活收拢成明天直接可用的状态；本地试做成功不代表备餐能过                       |
| 本地开发     | 关门内部试菜             | 在本机或开发环境边做边改；它不是公开试营业，也不能证明生产环境正常                   |
| 部署         | 把版本送到运行环境       | 可类比正式开业，但部署不天然等于流量已切换、用户可用或验收通过                       |

## 11. 前厅易混边界速查

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Props | 上级交给当前岗位的任务卡 | 父组件传入的值可以随下一次渲染变化，但子组件不能直接修改收到的 props |
| State | 当前岗位自己维护的现场记录 | 状态变化会推动组件更新；不要把它概括成全店实时人数 |
| Hooks | 使用 React 能力的函数接口 | 用于状态、上下文、引用和副作用等；不是“到点自动掏出的工具” |
| 服务端渲染（SSR） | 客人到店后按当次信息填完整菜单 | 服务器针对请求生成 HTML，再送到浏览器 |
| 静态生成（SSG） | 开门前预先印好固定版本菜单 | 页面在构建阶段生成；重新验证等混合策略要按框架能力另说 |
| JSON | 双方都认的数据记录写法 | 规定文本格式与值类型，不规定业务字段必须有哪些 |
| schema / 运行时校验 | 单据栏目与收单检查规则 | 决定字段、类型和约束；TypeScript 不能替代对外部输入的运行时校验 |
| WebSocket | 持续开着的双向对讲机 | 浏览器与服务器都能在连接上主动发消息 |
| SSE | 后厨向前厅持续广播 | 这条连接上主要是服务器单向推送；前端回话通常另发请求 |
| CORS | 你去隔壁店借了本菜单；封皮上没写“准你翻”，你就原样收着不翻开 | 翻不翻开是浏览器把关，“准不准翻”对应服务器的 CORS 响应头；请求可能已经发出，它不是认证或授权 |
| SEO | 把门牌、菜单与内容整理得便于搜索系统理解 | 有助于发现和呈现，不保证收录或排名；SSR 只是可选技术手段之一 |
| 浏览器存储 | 食客终端上的小抽屉 | localStorage、sessionStorage、IndexedDB 等机制边界不同，不天然适合存敏感凭据 |

# 二、后厨篇

> 场景故事：食客的请求经正式通道送到服务端——业务规则处理，必要时查账本、档案柜或库存，再把状态、数据或错误返回前端。小票夹只用于确实需要异步处理的支线，不是每张请求都排队。

## 1. 后厨基本盘（基础概念）

| 术语        | 餐厅类比                       | 一句话说透                                                               |
| ----------- | ------------------------------ | ------------------------------------------------------------------------ |
| 服务器      | 持续值守的后厨工位             | 可指服务器软件，也可能泛指承载机器；未必 24 小时运行                      |
| 数据库      | 账房、档案柜或库存系统         | 保存和查询持久数据；按数据内容选物件，用户和订单不能冻进冷库             |
| 接口（API） | 正式通道 + 通道规矩            | 约定地址、操作、输入、输出和错误；传菜员只是请求链中的角色               |
| CRUD        | 对记录的新记、查找、改正、删除 | 描述四类数据操作，不代表系统没有复杂业务规则                             |
| 业务逻辑    | 菜谱之上的店规                 | 会员折扣、售罄和退款等规则；故障可能来自规则、数据、依赖或实现多个层面   |

## 2. 菜系流派（编程语言）

> 编程语言可先记成不同**表达章法**。不要从菜系气质推导稳定性、性能或适用行业；这些结论取决于运行时、库、架构、团队和具体实现。

| 术语      | 餐厅类比             | 一句话说透                                                           |
| --------- | -------------------- | -------------------------------------------------------------------- |
| Java      | JVM 生态的一套章法   | 静态类型、JVM 与成熟生态是重要特征；不等于只服务银行或大厂             |
| Python    | 强调可读性的通用章法 | 常用于自动化、数据、AI 与 Web，也能承担其他领域                        |
| Go        | 编译型并发章法       | 内建并发工具并常用于网络服务；性能与部署仍需结合程序和平台判断          |
| PHP       | Web 生态成熟的章法   | 长期服务于服务端 Web，不能仅按“老店”判断是否适合                       |
| C# (.NET) | .NET 生态的章法      | 与 .NET 紧密结合，覆盖服务端、桌面、游戏等多种场景                     |
| Node.js   | JavaScript 的后厨工作台 | 它是运行时而非语言；让 JavaScript 在浏览器外运行                       |

## 3. 厨师学校（框架）

> 服务端框架可以先记成**操作规程与现成设施**。报技术栈时说明语言、运行时、框架和版本会更准确；“学校档次”不能当性能或项目规模结论。

| 术语        | 餐厅类比           | 一句话说透                                                      |

## 4. 账房、档案与存货（数据库与存储）

| 术语          | 餐厅类比           | 一句话说透                                                           |
| ------------- | ------------------ | -------------------------------------------------------------------- |
| MySQL         | 成熟的结构化账房系统 | 关系数据库之一；选择取决于数据、查询、团队与运维，不设“默认冠军”     |
| PostgreSQL    | 成熟的结构化账房系统 | 关系数据库之一，功能丰富；同样需要按工作负载和生态选择                |
| SQLite        | 随设备携带的单本账   | 嵌入式单文件数据库；可多读、同一文件同刻单写，低写并发场景很合适      |
| MongoDB       | 文档档案柜           | 文档结构可较灵活，也支持 schema validation，并非完全没有格式约束      |
| Redis         | 内存中的快速工作台   | 可做缓存、计数、会话、队列等；“缓存”不必然等于 Redis                  |
| Elasticsearch | 带倒排目录的检索室   | 擅长全文检索与聚合；不是主数据库的无条件替代品                        |
| SQL           | 结构化账房语言       | 用于查询和修改关系数据；安全、性能与事务仍需专门设计                  |
| 索引          | 档案目录             | 以空间和写入维护换特定查询更快；慢查询不一定只缺索引                  |
| 事务          | 一组成套入账动作     | 保证数据操作按隔离与原子性等规则完成；菜做熟无法真的回滚              |
| 表结构        | 账本栏目与约束       | 定义表、字段、关系和约束；迁移是受控的版本化变更步骤                  |
| ORM           | 两套记法的账房接口   | 映射对象与数据库操作，减少样板代码但不消除 SQL、性能和事务知识        |

## 5. 后厨后勤（中间件与基础设施）

| 术语     | 餐厅类比         | 一句话说透                                                               |
| -------- | ---------------- | ------------------------------------------------------------------------ |
| 消息队列 | 异步待办小票夹   | 适合无需当前请求一直等待的工作；能缓冲和解耦，消费者太慢仍会积压          |
| Kafka    | 可分区、可回放的流水卷宗 | 事件可保留并由消费者按位置读取；不写“吞吐量最大”的无条件排名       |
| RabbitMQ | 按规则路由的消息代理 | 通过 exchange、routing key、queue 和确认机制交付；延迟与重试需另设计 |
| 定时任务 | 每日固定流程     | 凌晨盘点、开市前熬高汤、半小时未取餐自动取消                             |
| 对象存储 | 外部包裹仓       | 按对象键保存图片、视频、备份等；URL 可能公开，也可能是有时效的签名地址    |

## 6. 点菜话术与会员制度（接口与鉴权）

| 术语        | 餐厅类比                | 一句话说透                                                                                       |
| ----------- | ----------------------- | ------------------------------------------------------------------------------------------------ |
| RESTful     | 以资源为中心的窗口话术  | 合理使用 URI、HTTP 方法和状态语义；不是所有 API 的默认或唯一风格                                  |
| GraphQL     | 按 schema 勾选所需栏目  | 客户端声明需要的字段，仍只能查询 schema 提供的能力；不是随意改菜                                  |
| RPC / gRPC  | 按约定呼叫远端工序      | RPC 是远程过程调用风格，gRPC 是一种实现；既可内部使用，也非绝对不能对外                           |
| 接口文档    | 菜单 + 传菜规范手册     | 地址、参数、返回格式全写清，前厅后厨靠它对齐；Swagger = 能现场试点的电子菜单                     |
| JWT         | 带签章的声明手牌        | 可签名并带有效期；签名不等于加密，被盗仍可冒用，撤销策略需另设计                                 |
| OAuth 2.0   | 有范围的代办授权书      | 让第三方获得有限访问权；它本身不是身份协议，用于登录通常结合 OpenID Connect                       |
| SSO         | 集团统一验人            | 一次登录后访问多个关联系统；与 OAuth 解决的问题不同，具体实现可采用 OIDC、SAML 等                  |
| 限流与熔断  | 高峰限号 / 菜品临时停售 | 限流 = 每小时最多放 50 桌，超了请排队；熔断 = 某供货商断了就先停售那道菜，别把全店拖死           |

## 7. 开店与守店（部署与运维）

| 术语             | 餐厅类比                   | 一句话说透                                                                               |
| ---------------- | -------------------------- | ---------------------------------------------------------------------------------------- |
| Linux            | 后厨基础操作环境           | 操作系统内核与生态提供进程、文件、网络等能力，不等于建筑材料                             |
| Nginx            | 门口接待与分流台           | 可托管静态文件、反向代理、负载分发与终止 TLS；HTTPS 不是“验会员”                         |
| 负载均衡         | 多个出餐口的叫号分流       | 一个出餐口扛不住就开三个，有一个关了自动不往那派                                         |
| Docker           | 标准厨房箱                 | 封装应用与运行依赖以提高环境一致性；秘密、持久数据和外部服务通常不进镜像                 |
| Kubernetes (K8s) | 厨房箱调度系统             | 管理部署、扩缩、恢复和服务编排；是否采用看复杂度和运维能力，不看固定数量门槛             |
| 云服务器         | 商场里的租赁工位           | 租用计算资源；定价、弹性、可用性和管理责任以具体云产品与配置为准                         |
| CI/CD            | 版本交付流水线             | 持续集成与持续交付/部署的自动化程度不同，不保证所有环节完全无人介入                     |
| 日志             | 带时间与标识的工作记录     | 是排障证据之一；完整观测还可能需要指标、追踪、事件和现场状态                             |
| 监控告警         | 烟感报警器 + 值班巡场      | 盯着温度、火情、出餐速度，异常自动打电话叫人                                             |
| 域名与 HTTPS     | 门牌号 + 验明身份的密封传话袋 | 域名定位服务；HTTPS 通过 TLS 提供身份校验、加密与完整性，不代表网站内容安全             |
| HTTP             | 请求与响应的通用传话规矩   | 点击可能触发请求，但按钮本身不是 HTTP；服务端返回的是响应而非同一张请求单                 |
| 端口             | 同一地址下的编号入口       | 先把连接交给某个服务；进入服务后再由路由匹配路径，二者不能混为一谈                       |
| CDN              | 连锁分店 / 前置仓          | 招牌半成品铺到离食客近的分店，外地食客不用等总店跨省配送                                 |
| 重定向           | “请改去另一个地址”指路牌   | 3xx 状态码表达不同跳转语义；301 常用于永久迁移、302 常用于临时跳转，缓存与方法行为要看具体码 |
| 数据校验         | 点菜核对                   | "您确定特辣？这份很辣"——前厅核对为体验，后厨出菜前再核对才是底线                       |
| 认证与授权       | 验身份 vs 看权限           | 认证 = 确认你是不是会员（你是谁）；授权 = 会员能不能进包厢（你能干啥）                   |
| 功能开关         | 新菜内部试卖               | 先只给熟客，有问题立刻撤下，不用换整本菜单                                               |
| Serverless       | 平台代管的按需厨房能力     | 平台负责较多基础设施并按用量扩缩或计费；空闲成本、冷启动和限制因产品配置而异              |

| 术语             | 餐厅类比                 | 一句话说透                                                                   |
| ---------------- | ------------------------ | ---------------------------------------------------------------------------- |
| 异常与堆栈       | 出错点与调用路径记录     | 堆栈主要给出程序调用路径；时间、请求人和上下文还要靠日志与追踪补齐              |

| 超时             | 等过约定期限便停止等待   | 客户端、网关、服务和数据库可有不同期限；是否取消底层工作与是否重试要另行设计    |
| 连接池           | 常驻传菜员编制           | 固定几个传菜员随时待命，不现招；"连接池满了" = 传菜员全派出去了，新单排队    |

| 中间件（请求层） | 进后厨前的安检传送带     | 每张单子必经：验真伪、查限号、登记——统一加规矩都挂在这条带上               |

## 9. 安全与架构（第三轮补充）

| 术语           | 餐厅类比                          | 一句话说透                                                                                               |
| -------------- | --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 微服务与单体   | 大厨房 vs 独立档口群              | 拆分可支持独立部署与团队边界，也会增加网络、一致性和运维成本；不能按人数自动决定                         |
| 接口分页       | 档案分批翻阅                      | 页码与游标是不同策略；游标应基于稳定排序键，是否重复或漏项仍取决于数据变化和实现                          |
| 加密与哈希     | 可开保险柜 / 带盐的单向核验       | 需恢复原文的数据用加密；密码用专用、带盐且有成本参数的密码哈希，算法选择不能省                           |
| SQL 注入       | 把来客文字混进账房命令            | 首选参数化查询或预编译语句，并配合最小权限；只做输入“消毒”不够                          |
| XSS            | 来客内容被前厅当成可执行机关       | 按输出上下文编码、使用安全 DOM API，允许 HTML 时专用清洗，CSP 作为纵深防御              |
| 数据备份       | 每天把账本复印存隔壁保险柜        | 铁律：没演练过"从复印件恢复"的备份等于没备份                                                             |

## 10. 容易被一句话糊住的工程边界

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| SDK | 供应商交付的整套订货工具包 | 常含代码库、类型、工具与文档，不只是一句专用话术 |
| 多环境 | 开发、演练与正式店分开 | 配置、数据和权限应隔离；同一构建产物是否跨环境复用要看交付策略 |
| 环境变量 | 开工时传入的一种配置纸条 | 不是秘密保险箱；密码和密钥应由秘密管理系统保护，避免进仓库和镜像 |
| 功能开关 | 暂时决定某项服务是否开放 | 能控制功能，不自动构成按指标推进的灰度发布策略 |
| 灰度发布与回滚 | 先放少量客流，观察后推进或撤回 | 要预先定义人群、指标、停止线以及代码、配置和数据的兼容方式 |
| Append-only | 账本只加新行，更正也另记一笔 | 表示记录策略，不等于文件或数据库天然不可篡改 |
| JSONL | 一行一份 JSON 记录 | 便于流式处理；它是格式，不保证顺序、完整性或不可修改 |
| 适配器模式 | 老设备前加转换接头 | 让不兼容接口协作，不改变被适配对象原本能力 |
| 依赖注入 | 岗位声明所需设备，由店里按环境配给 | 关注依赖由外部提供；不等于用了某个容器才算依赖注入 |
| 管道模式 | 结果依次交给下一工序 | 每段仍需明确输入输出、失败、重试与是否可重复执行 |

# 三、厨师篇

> 场景故事：现在你是餐厅老板，店里有一位厨师长和一位值班经理。你把要办的事交代给经理，经理带着任务和资料去找厨师长商量；厨师长负责判断，库管、收银员和设备按要求动手。厨师长不知道你没交代的情况，记性有限，也可能一本正经地说错。怎么交代、怎么安排代办、怎么验收，就是"AI 协作"的全部学问。

讲 AI 控制流程时要分清两层：**大模型对应厨师长，负责判断或提出代办请求；Agent 是厨师长、负责调度的值班经理以及按场景办事的店员或设备合在一起的班子。** 全程沿着“交代—代办—回报—再商量”走，不能把模型的回话一会儿说成菜、一会儿又说成传菜单。所有角色都必须是现实餐厅中存在的岗位，不得靠“远程”“虚拟”“智能”等前缀生造角色。落到具体动作时说“库管查库存”“库管回来报数”“收银员翻账”，不要让“店内工具”这个抽象词假装成人，也不要在结尾写“厨师给出最终答复”；直接写师傅实际说了什么。

## 1. 跟厨师说话的基本功（AI 对话基础）

| 术语                 | 餐厅类比                      | 一句话说透                                                                                          |
| -------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------- |
| Token                | 传话纸上的计量格              | 输入和输出都会占格，许多服务也据此计费；切分方式与价格按模型和供应商而异                                  |
| 上下文窗口           | 商量桌一次能摊开的材料总量    | 超限可能报错、截断或压缩，取决于产品与配置；不能承诺最早内容必然自动掉出                                  |
| 上下文工程           | 整理本轮商量材料              | 选择、组织并按需提供规则、代码、历史和工具说明；错了要回查材料与模型两边                              |
| 上下文压缩           | 把前半场经过写成小抄          | 将早先材料摘要化以腾出空间；摘要有损，关键约束应留在可查的正式来源                                    |
| 上下文文件           | 可按规则翻阅的店规文件        | 是否自动加载、何时加载由宿主和文件位置决定；写进文件不等于模型永久记住                                |
| 系统提示词           | 平台贴在商量室的上位规矩      | 由平台或应用设置，不是模型给自己立规矩；产品还可能有其他高优先级指令层                                  |
| 提示词               | 当前交代与所给材料            | 说明目标、必要背景、约束和成功标准；角色、样例并非每次都必须硬凑                                        |
| 思维链               | 得出结果时的中间推理          | 不要求暴露隐藏原始推理；需要审查时索要计划、关键依据、计算步骤或验证结果                                  |
| 示例驱动             | 给厨师看合格样菜与反例        | 样例能约束格式和边界，也会复制样例里的偏差；不是越多越好                                              |
| 对话历史             | 本轮实际带入的沟通记录        | 只有应用放进当前上下文的消息才会被本次调用看到，不等于天然拥有全部历史                                |
| 无状态请求           | 每轮商量都要重报前情          | 模型调用本身不记事，每次调用都要由外层程序把需要的前文重新带上                                      |
| 记忆                 | 熟客档案                      | 跨会话保存偏好或事实；保存多久、谁可见、能否删除取决于产品，不能承诺永久                                |
| 多模态               | 厨师还看得懂照片              | 不只是听得懂话——把卖相照片拍给他，比形容一百句准                                                  |
| AI 幻觉              | 说得像真的却没有可靠依据      | 语气不是证据；涉及事实要核对一手来源、工具结果、代码或测试                                            |
| 大模型               | 负责判断和生成的厨师长        | 只取“按交代与材料产出内容”这一点；模型没有人的理解、责任或现场经验                                    |
| 模型供应商与兼容接口 | 劳务公司 + 相近的对讲格式     | 部分接口采用相近格式，但字段、流式事件、工具调用、错误与能力不保证完全兼容                                |
| 会话中切换模型       | 下一轮换一位厨师长            | 应用若完整重放上下文未必丢信息，但行为、格式、工具和上下文能力可能变化                                    |
| 思考模式与推理强度   | 让他多分配一些推理量          | 支持方式、延迟和计费因模型而异；不能一概写成档位越高一定更贵更准                                          |
| 结构化输出           | 按固定栏目交回记录            | 要求输出匹配 JSON schema 等结构；消费者仍需验证解析和业务约束                                         |
| 流式响应             | 师傅的话一句句说出来          | 师傅还没说完，前面的话已经先传到；传来的是本轮输出，不代表店里的工具已经执行                        |
| 轮次与轨迹           | 一轮商量 / 全部商量与办事记录 | 一次模型调用是一轮；工具代办和再次调用由外层继续推动                                                |
| 停止原因             | 这一轮为什么结束              | 它本身是调用结束后返回的技术标签；`stop` 和 `tool_use` 都只结束当前轮，后者表示留下了代办请求   |
| 提示词缓存           | 复用没变的前半叠材料编排      | 通常要求重复前缀满足供应商规则；保留时间、命中范围和折扣都不能写死                                        |
| 渐进式披露           | 档案库先给目录                | 先提供摘要与索引，任务需要时再加载细节，减少无关上下文                                                |
| 对话分叉             | 试菜开两条线                  | 从某个节点起，一条线试辣、一条线试不辣，旧线留着随时能回去                                          |
| 会话持久化与恢复     | 保存商量记录，之后接着办      | 应用保存到什么程度决定能否恢复；“保存了”不保证外部副作用也能回到原状态                                    |
| 插队指令与追加任务   | 商量时补话 / 下一轮再交代     | 能否立刻打断取决于系统；排进下一轮的要求，要等下一次模型调用才会收到                                |
| Steering 消息注入    | 下一轮商量前补一句要求        | 值班经理把新要求加入下一轮上下文，已经结束的上一轮不会提前收到                                      |
| Vibe Coding          | 不会做饭的人用自然语言带店    | AI 可承担大量实现，但人仍负责需求、权限、安全、测试和验收，不能概括成“厨师全包”                       |

## 2. 让厨师自己张罗（Agent 与工具）

| 术语               | 餐厅类比                             | 一句话说透                                                                                                 |
| ------------------ | ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| AI Agent           | 厨师长 + 值班经理 + 店员或设备       | 大模型负责判断和发请求，外层程序负责调用模型、代办、回传；合起来才是 Agent                                 |
| 编码智能体         | 你的驻店厨师长                       | 专门帮你读菜谱、改菜、跑厨房的那类 Agent（Kimi Code、Claude Code、Cursor 都是）                            |
| LLM 抽象层         | 经理统一几家劳务公司的联络方式       | 能统一常见调用，但抹不平模型能力、工具格式、流式事件和错误语义的全部差异                                   |
| 工作流             | 预先编排的工序与分支                 | 由人或系统先定义步骤、条件和错误路径；可包含判断，不等于完全没有分支                                     |
| 计划模式           | 先写方案再决定是否动手               | 是部分产品提供的工作方式；是否必须审批及允许哪些动作以具体系统规则为准                                     |
| 权限模式与 YOLO    | 逐项授权 / 较宽范围自动执行          | 宽权限会放大误删、泄露和外部副作用；授权范围应与风险和可恢复性匹配                                          |
| 沙箱               | 有边界的试验厨房                     | 限制文件、网络、进程等可访问范围；边界配置不严或另有授权时仍可能影响外部                                  |
| 人在回路           | 高风险节点由人复核                   | 是否要求确认取决于权限政策；付款、删除、发布等高风险动作通常应设人工关口                                   |
| 可观测性           | 透明厨房与工作记录                   | 记录模型输入、工具调用、耗时、成本、错误和结果；同时要防止秘密与个人数据泄露                               |
| 工具调用           | 厨师长请店里代办                     | 他发出结构化请求；值班经理再让库管、收银员或具体设备动手，不是模型亲自执行。不要另造“取料单”或“代办单” |
| 工具结果           | 办事的人回来报结果                   | 成功、失败和查到的内容先报给值班经理，经理在下一轮商量时告诉厨师长                                         |
| 双层消息模型       | 给老板看的回话 / 给厨师长看的办事记录 | 是部分 Agent 的应用层设计，不是所有模型接口的通用结构                                                       |
| 错误即消息         | 办砸了也照实回报                     | 把失败类型、上下文和可重试信息结构化回传，让外层或下一轮决定如何处理                                       |
| 外层 followUp 循环 | 值班经理带结果再找厨师长             | 厨师长请人代办，店里办完回报，经理带着结果再去商量；如此继续，直到事情说清或必须停下                       |
| 工具输出截断       | 盘点报告太长只带摘要                 | 完整内容是否另存、能否再取由系统决定；摘要要保留错误、关键证据和定位信息                                   |
| MCP                | AI 应用与外部能力的标准接口          | 服务器可暴露 tools、resources、prompts；宿主负责连接、协商、授权与安全边界，模型不会直接任意访问            |
| Skill              | 按需翻阅的岗位手册与资源包           | 在触发时加载说明和资源，不等于永久训练模型，也不保证只报名称就一定正确执行                                  |
| 钩子               | 特定节点自动触发的检查或动作         | 触发时机和能做什么由具体产品决定；并非所有改动都天然经过同一钩子                                           |
| 斜杠命令           | 产品提供的快捷入口                   | 具体语义由产品定义；有些改变会话设置，有些只是插入提示，不能一概说“不是对话”                               |
| 扩展与插件         | 给厨房加装新设备                     | 在主体之外增加能力；安装前核对来源、权限、依赖和数据去向                                                   |
| TUI                | 在文字终端里操作的前台               | 以终端文字界面交互；它与“无头模式”不是同义词                                                              |
| 无头模式           | 不依赖可见前台的后台运行             | 由脚本或服务调用，不等于全自动，也不代表无需权限和人工验收                                                 |
| Sub-agent          | 分工的帮厨                           | 把边界清楚的子任务交给其他 Agent；不一定并行，也要处理共享状态、冲突和汇总                                 |
| 多 Agent 编排      | 整个厨师班组                         | 凉菜、热菜、面点、传菜分工协作，像后厨班组而不是一个厨师                                                   |
| 分支摘要           | 每条试菜线各留交接小结               | 摘要帮助汇总并会丢细节；关键证据仍要能回到原记录                                                           |
| ReAct              | 先判断一步、请办一步、看回报再判断   | 不一次猜完十步，先根据真实结果决定下一步                                                                   |
| Agent 循环         | 交代 → 代办 → 回报 → 再商量          | 循环由外层程序推动；要提前定好次数、预算、超时和失败出口，避免在错误上空转                                 |
| Harness            | 厨房的布局、动线与规章制度           | 厨师总在同一个地方滑倒，该改的是厨房地面，不是换厨师                                                       |
| 事件驱动与发布订阅 | 事件贴上主题后通知订阅岗位           | 生产者与消费者解耦；交付保证、重复、顺序和失败处理仍需另行设计                                             |
| RAG                | 先检索档案再把片段带来商量           | 能补充知识与出处，但不保证检索正确或模型不瞎编；权限、引用与无结果行为仍需设计                              |
| 微调               | 用训练样本调整模型行为               | 主要改变行为或任务表现；RAG 主要补运行时知识，选择取决于问题而非固定的价格顺序                              |
| 提示词注入         | 外来材料夹带“改店规”的话             | 把外部内容当数据、隔离指令与数据、限制工具权限、校验参数，高风险动作前人工确认                             |
| TTFT 与 TPS        | 首句多久到 / 持续说话速度            | TTFT 是首个输出片段延迟；TPS 是持续生成吞吐，Token 口径按供应商定义                                        |
| Token 用量与成本   | 统计传话纸用了多少格                 | 按任务核对输入、输出、缓存与推理相关用量；具体计费口径查供应商合同                                          |
| 速率限制           | 单位时间接待量上限                   | 可按请求或 Token 等口径限制；超限可能返回 429、排队或要求退避，按服务契约处理                               |

## 3. 验收（提需求与验收）

| 术语     | 餐厅类比       | 一句话说透                                                                                      |
| -------- | -------------- | ----------------------------------------------------------------------------------------------- |
| 验收标准 | 试菜验收清单   | 咸淡、温度、摆盘逐条可打勾；没有清单，厨师说"做好了"你无法判断真假                              |
| 测试用例 | 关门演练剧本 | “给定一张订单→执行哪些步骤→应看到什么结果”；有精确输入、动作和预期才便于复现与判断             |

# 四、类比的边界：哪里会失真

类比是脚手架，不是真相。理解入门后，这几处"餐厅"会露馅，要知道：

1. **软件复制的边际成本很低，但不是绝对零成本。** 分发、带宽、存储、计算和运营仍要花钱；菜品复制则每份都需要明显的物料与制作成本。所以“开源”“规模化”的经济结构不能照搬餐厅画面。
2. **代码可以回到已记录版本，菜做坏就是坏了。** `git` 版本管理像一台只在拍过快照处停靠的“时间机器”；未记录改动、数据库和外部副作用不一定跟着恢复，餐厅画面讲不清这些边界。
3. **记录可以描述使用系统的人。** 用户既发起操作，数据库里也可能保存他的账号资料；餐厅里的食客和写着食客资料的档案并不是同一个东西，不能把“本人存进冷库”。
4. **前厅和后厨可以跑在不同城市。** 前端在食客手机（他家餐桌）上，后端在千里之外的机房里——餐厅类比掩盖了"网络延迟"这个真实世界的大问题。
5. **机器不会累，但会"整整齐齐地错"。** 厨师累了会手抖，机器不会——它只会把同一个错误用完全相同的方式重复一百万次。所以程序的 bug 是"系统性"的，比人的失误更隐蔽也更整齐。

> 用法建议：先用本手册建立角色、方向和作用的直觉，再回项目文档、代码、测试与官方资料核对定义和边界。类比只管“先听懂”，证据才管“能判断”。
