# 餐厅类比手册：用一家餐厅理解所有编程术语

> 用途：让完全不懂编程的人（比如一位餐厅服务员），也能理解每个编程术语"是做什么的"。
> 方法：把整个软件世界映射成一家餐厅。遇到任何生词，先问三个问题——**它在餐厅的哪个位置（前厅/后厨/仓库/路上）？它服务谁？它坏了餐厅会怎样？**
> 与其他手册的关系：前端、后端、AI 协作三份手册管"这个词的准确定义和用法"，本手册管"这个词的第一印象"。先在这里建立直觉，再去查对应手册的正式词条。

# 〇、总设定：整个软件就是一家餐厅

## 核心映射总表（先背这 12 个，其他全是它们的展开）

| 编程概念 | 餐厅类比 | 一句话说透 |
|---|---|---|
| 一个软件产品 | 一家餐厅 | 食客（用户）来消费，前厅招待，后厨做菜 |
| 用户 | 食客 | 只接触前厅，从不进后厨 |
| 前端 | 前厅大堂 | 食客看到、摸到、点到的一切 |
| 后端 | 后厨 | 食客看不见但真正做菜的地方 |
| 数据库 | 冷库与仓库 | 所有食材（数据）长期存放的地方 |
| API（接口） | 传菜窗口 + 传菜员 | 前厅和后厨之间唯一的官方通道 |
| 程序员 / AI 写代码 | 厨师做菜 | 把原料变成成品的劳动 |
| 编程语言 | 菜系 / 厨艺流派 | 川菜、粤菜、淮扬菜——都是做菜，章法完全不同 |
| 框架 | 厨师学校的教学体系 | 新东方、蓝带——同一菜系里不同的"标准操作规程" |
| 大模型（Claude、GPT 等） | 厨师的大脑（厨艺本身） | 不同牌子 = 不同水平的厨师 |
| IDE / 编程工具 | 灶台与锅具 | 厨师干活的家伙什 |
| Harness | 厨房的布局、动线与规章制度 | 厨师总在同一个地方出错，该改的是厨房，不是换厨师 |
| 上线部署 | 开业迎客 | 从试菜到正式开门 |

## 为什么这个类比成立

餐厅和软件有同构的"三层 + 通道"结构：

- **食客只接触前厅** ↔ 用户只接触前端页面；
- **前厅不下厨，后厨不见客** ↔ 前端不管数据，后端不管长相；
- **前厅后厨通过传菜窗口对话，且有标准话术** ↔ 前后端通过 API 通信，且有固定格式；
- **食材要冷藏、要盘点、怕丢怕坏** ↔ 数据要存储、要备份、怕丢怕错；
- **饭点会挤爆、厨师会出错、新菜要试卖** ↔ 系统有高并发、有 bug、要灰度发布。

> 对最初设想的微调：原设想里"Python、Java = 不同的锅铲"。本手册改为"菜系/厨艺流派"——因为语言决定的是**做菜的章法和思维方式**（同样是鱼，川菜水煮、粤菜清蒸），而锅铲只是工具，更接近 IDE。这样整个体系里"工具（锅具）= IDE、厨艺（大脑）= 大模型、章法（菜系）= 编程语言"各归其位，不会互相打架。

# 一、前厅篇（对应《前端技术词汇手册》）

> 场景故事：一位食客推门进店——他看到的装修、坐下的桌椅、递上的菜单、服务员的应答、桌上的叫号屏……这一切就是"前端"。食客永远不会进后厨，他对这家店的全部印象都由前厅决定。

## 1. 前厅的硬装与软装（网页基础）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| HTML | 前厅的空间结构 | 哪里是门、哪里是吧台、摆几张桌子——只管"有什么"，不管好不好看 |
| CSS | 装修与摆盘 | 灯光、桌布、餐具摆放、上菜的卖相——90% 的"改好看点"都改在这层 |
| JavaScript | 前厅会动的机关 | 点餐铃、叫号屏、自动门——一切"有反应"的东西背后都是它 |
| TypeScript | 带编号核对单的传菜系统 | 每个托盘有编号、上菜前对单，上错菜当场发现，而不是等食客投诉 |
| 浏览器 | 食客坐的那套餐桌椅 | 同一道菜，坐高背椅和坐塑料凳体验不同——"兼容性问题"就是桌椅不统一 |
| WebAssembly | 请进前厅的特级厨师现场表演 | 火焰冰淇淋、拉面秀——前厅原本干不了的重活，借调后厨高手来现场做 |

## 2. 服务流派（框架层）

> 框架 = 前厅的**服务流程体系**。同样是招待食客，麦当劳有麦当劳的话术动线，海底捞有海底捞的——换个框架，等于把前厅的整个服务体系换掉，所以跟"厨师"（AI）下指令时必须先说清楚用的是哪套。

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| React | 麦当劳体系 | 全球最大连锁的服务体系，把服务拆成标准动作模块拼装，培训资料最多 |
| Vue | 本土家常菜馆体系 | 国内最流行的服务规范，上手快，规矩贴近本土习惯 |
| Angular | 国宴级全套礼仪 | 规矩最多但什么都管，大型宴请（大企业）才用得上 |
| Svelte | 新式轻简服务 | 环节少、动作快，新派餐厅口碑很好 |
| SolidJS | 实验餐厅体系 | 流程像麦当劳但更精细更快，敢尝鲜的店在用 |
| Qwik | 翻台率至上的快餐体系 | 食客进门 3 秒内必有人招呼，为"秒开"极端优化 |

## 3. 统一采购的餐具与服务包（组件库）

> 组件库 = 统一采购的**成套餐具 + 标准服务包**。自己烧瓷打碗又贵又不统一，直接整套买——"先声明用哪套餐具，AI 就不会自己手搓碗筷。"

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Ant Design | 企业商务宴请套装 | 国内商务宴请的标配，沉稳、什么场面都撑得住 |
| Element Plus | 国民连锁餐饮套装 | 本土连锁主流，中文说明书友好 |
| Material UI | 国际连锁ins风套装 | 海外流行，风格现代、细节精致 |
| Arco Design | 网红年轻品牌套装 | 设计偏年轻，中英文档都友好 |
| Naive UI | 小众精品店套装 | 轻便、好定制，回头客口碑好 |
| Chakra UI | 无障碍友好餐厅套装 | 轮椅通道、盲文菜单都想好了，定制也灵活 |

## 4. 连锁加盟的开店手册（应用框架）

> 应用框架 = **加盟总部给的一整本开店手册**：装修图纸、动线设计、员工培训、开业流程全写好，照着做就能开出一家像样的店。

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Next.js | 麦当劳加盟手册（React 系） | 自带"大众点评收录"服务（SEO），做要被搜到的店首选 |
| Nuxt | 本土连锁加盟手册（Vue 系） | Vue 体系对应的开店手册 |
| SvelteKit | 新派小店加盟手册（Svelte 系） | Svelte 项目的标配开店手册 |
| Ant Design Pro | 商务宴请的"拎包开店"方案 | 迎宾、包厢管理、账单系统全是现成的，搭管理系统直接用 |

## 5. 开业前的备料流水线（构建层）

> 构建工具 = **开业前的备料备餐流水线**：把毛菜（源代码）洗切配、预处理成净菜包（浏览器能直接加载的文件）。普通沟通只需知道自家店用哪条流水线，出问题时把名字报给"厨师"。

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Vite | 新一代高速备料线 | 开机快、出菜快，现在新店的绝对主流 |
| Webpack | 老式备料线 | 功能全但慢、操作复杂，大量老店还在用 |
| Rollup | 精品外卖包装线 | 专打"小而干净"的包，给别的店供货的中央厨房用 |
| Rspack | 老式流水线的高速改装版 | 老店的备料线近乎零成本提速 |

## 6. 水电气与采购部（转换层）

> 这一层食客完全感知不到，但没有它餐厅一天都开不了张。

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Node.js | 后厨的水电气 | 一切运转的能源基础；也让"前厅服务员的话"（JavaScript）在后厨能听懂能干活 |
| npm | 采购部（默认） | 拿着供应商名录去批发市场订食材（依赖包）的那个部门 |
| pnpm | 精明的采购部 | 订得快、仓库占用省，管多家分店时尤其好用 |
| Yarn | 老牌采购部 | 早年解决了默认采购部又慢又乱的问题，老店常见 |
| Bun | 新锐全能后勤 | 采购、备料、质检一人全包，卖点是快，还在成长期 |

## 7. 外卖与餐车（延伸领域 · 移动端）

> 做手机 App = 餐厅不满足于堂食，开始做**外卖和餐车业务**。

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| React Native | 用堂食班底开外卖车 | 一套班底同时出 iOS、安卓两辆餐车，前厅团队转型的最短路径 |
| Flutter | 专业外卖车队 | 车况好、各车出品一致，但和堂食班底基本不通用 |
| Swift | 苹果商圈的专卖店 | 只做苹果商圈生意，按人家规矩来 |
| Kotlin | 安卓商圈的专卖店 | 只做安卓商圈生意 |

## 8. 前厅的共享信息（状态管理）

> 状态管理 = 前厅的**共享白板 + 全员对讲机**："3 号桌是 VIP""7 号桌过敏不吃花生"——所有服务员实时同步。小餐馆靠吼就够了，店大了必须有白板。

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Redux | 最严格的看板管理制度 | 规矩多、填写繁琐，但每一条记录可追溯，大团队爱用 |
| Pinia | Vue 系官方白板 | 本土体系官方推荐，简单直观 |
| Zustand | 便利贴墙 | 几行字就建一块信息区，中小店替代严格看板的热门选择 |
| Vuex | 老式白板 | 老店常见，新店建议直接用官方新白板（Pinia） |

## 9. 传菜员的装备（数据请求）

> 数据请求 = 传菜员的**对讲机和点单 Pad**——前厅找后厨要菜全靠它。

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Axios | 标准对讲机 | 前厅后厨通话几乎都用它，最流行 |
| SWR | 带记忆的对讲机 | 问过一次的事先按上次答案回话，再悄悄核实更新，食客不用干等 |
| React Query | 智能对讲机 | 记忆、自动重问、分页传菜全内置，React 店的主流装备 |

## 10. 前厅杂项

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Tailwind CSS | 预制调料包式装修 | 不写装修图纸，直接拼现成的风格模块（"ins 风 + 原木 + 暖光"），AI 最喜欢用，因为好改 |
| Three.js | 前厅的全息投影 / 3D 表演 | 产品 3D 展示、炫酷特效，镇店噱头 |
| 组件 | 标准化服务单元 | "迎客—引座—倒水"这套动作是个组件，哪个店门口都能复用；改一处，全部门店一起变 |
| 路由 | 前厅分区图 | 靠窗区、包厢区、吧台区——报位置（URL）就知道去哪个区域；"404"就是"您要的位置不存在" |
| 依赖 | 外购食材与设备 | 不是自己种的养的，全记进货单（package.json）上；"加依赖" = 引入新供应商 |
| 构建打包 | 打烊备餐 | 把今晚的活收拢成明天直接可用的状态；本地试做成功不代表备餐能过 |
| 本地开发 | 试营业 / 内部试菜 | 不对外，边做边尝边改 |
| 部署 | 正式开业 | 从试营业到开门迎客；"部署后样式丢了" = 开业发现和试营业时装修不一样 |

# 二、后厨篇（对应《后端技术词汇手册》）

> 场景故事：食客点的每一道菜，都经传菜员送进后厨——灶台前厨师掌勺，冷库里食材进出，小票夹上一单单排队，凌晨有人盘点熬汤。食客永远看不到这里，但菜的味道、速度、安全全由后厨决定。

## 1. 后厨基本盘（基础概念）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| 服务器 | 后厨本身 | 一间 24 小时开火的厨房，食客访问网站 = 隔着传菜口跟它说话 |
| 数据库 | 冷库与仓库 | 所有要长期保存的食材（用户、订单）都放这，前厅任何东西追根溯源都来自这 |
| 接口（API） | 传菜窗口 + 传菜员 | 前厅要菜走窗口、递单子，窗口有"地址、参数、返回格式"三要素 |
| CRUD | 食材的入库、取用、改标签、报损 | 后厨 80% 的活就这四样；说"这就是个 CRUD 系统"= 没硬菜，全是日常 |
| 业务逻辑 | 菜谱之上的店规 | 会员日打折、售罄不能点、退菜原路退回——bug 大多不是菜做错了，是规矩漏了 |

## 2. 菜系流派（编程语言）

> 语言 = 厨师的**菜系功底**。同样是做鱼，川菜水煮、粤菜清蒸——选语言就是选厨师的流派。

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Java | 国宴淮扬菜体系 | 最稳重大气，银行和大厂的宴席都靠它撑 |
| Python | 家常菜 | 最接近家常做法，上手快，炒菜、熬汤、做甜品（脚本、AI、数据分析）通吃 |
| Go | 高效中央厨房体系 | 出餐极快、一份配方（编译产物）推到哪里都能开火，云时代基础设施的主力 |
| PHP | 老牌大众食堂 | 曾经遍地开花，大量老店还在用，新大店较少选它 |
| C# (.NET) | 机关单位食堂体系 | 微软出品，企业软件圈子里很强 |
| Node.js | 前厅服务员转岗进后厨 | 本来在前厅干活的语言也能掌勺，全栈的最短路径 |

## 3. 厨师学校（框架）

> 框架 = 后厨的**操作规程体系**：同一菜系，不同学校教出的章法不同。报技术栈必须"菜系 + 学校"配对（淮扬菜 + 某校），单报菜系厨师不知道按哪套规矩来。

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Spring Boot | 国宴厨师学院 | 国宴系（Java）的绝对主流院校，大场面标配 |
| FastAPI | 新派快厨学校 | 家常菜系（Python）的新式学校，出菜快、自带菜单说明书，AI 店首选 |
| Django | 全能烹饪技校 | 从切配到收银全教，做内部食堂和内容型店极快 |
| Flask | 小灶速成班 | 只教基本功，其他靠自己添，适合先试菜 |
| Express | 前厅转岗速成班 | Node 系最经典的入门班，资料最多 |
| NestJS | 前厅系的正规军学院 | Node 系做大店的正规军校，分层清晰 |
| Gin | 中央厨房快训营 | Go 系最常用的轻量规程 |
| Laravel | 大众食堂翻新班 | PHP 的现代标准，老字号翻新都按它来 |

## 4. 冷库与存货（数据库与存储）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| MySQL | 国民品牌冷库 | 最流行的冷库，资料多、够便宜，说到"冷库"默认就是它 |
| PostgreSQL | 高端多功能冷库 | 分区更精细、功能更强，近年新店增长很快 |
| SQLite | 家用小冰箱 | 一台冰箱就是一个仓库，适合试菜和小店，人多抢用就不行 |
| MongoDB | 自由储物架 | 不规定每层放什么、随时改格局，适合菜单天天变的店 |
| Redis | 灶台边的随手调料架 | 最常用的（验证码、登录态、秒杀库存）放手边，秒取；"加缓存"就是添置它 |
| Elasticsearch | 仓库寻宝专家 | 你说"差不多的那个酱"他也能翻出来——模糊搜索、按相关度排序是他的绝活 |
| SQL | 跟库管说话的行话 | "写条 SQL 查一下" = 用行话直接问冷库要东西 |
| 索引 | 货架标签目录 | 没标签找一盒豆腐翻全库，有标签直接定位；找东西慢八成是标签没贴 |
| 事务 | 套餐不可分割 | 一鱼三吃，要么三道上齐要么整单退掉，不能上了两道第三道没了 |
| 表结构 | 仓库货架设计图 | 几个库区、每层放什么、通道怎么走；改设计图叫"迁移"（migration） |
| ORM | 双语领班 | 把厨师的口味语言自动翻译成库管的货架语言，不用厨师自己学说行话 |

## 5. 后厨后勤（中间件与基础设施）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| 消息队列 | 传菜口的小票夹 | 下单后不立刻发短信，往夹子上一插，专人按顺序处理；饭点削峰、环节互不累垮 |
| Kafka | 海量订单传送带 | 吞吐量最大的小票系统，专接大客流的行为流水 |
| RabbitMQ | 精准派单小票系统 | 路由灵活可靠，"30 分钟未支付自动取消"这类精细活靠它 |
| 定时任务 | 每日固定流程 | 凌晨盘点、开市前熬高汤、半小时未取餐自动取消 |
| 对象存储 | 外租大型冻库 | 大件（图片、视频）不堆自家厨房，租专业冻库，用时取一张提货单（URL） |

## 6. 点菜话术与会员制度（接口与鉴权）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| RESTful | 传菜窗口标准话术 | "报桌号取菜（GET）、下单（POST）、改单（PUT）、退单（DELETE）"——说"设计个接口"默认就是这套话术 |
| GraphQL | 食客自由定制 | "只要肉片不要葱，米饭减半"——要什么给什么，灵活但后厨累 |
| RPC / gRPC | 后厨各部门的内线电话 | 凉菜间打给切配间的内部线路，不走对客的传菜窗口 |
| 接口文档 | 菜单 + 传菜规范手册 | 地址、参数、返回格式全写清，前厅后厨靠它对齐；Swagger = 能现场试点的电子菜单 |
| JWT | 会员手牌 | 进店发一个手牌，之后享受服务都凭它；手牌有过期时间，过期重新领 |
| OAuth / SSO | 商场联名卡 / 集团一卡通 | 微信登录 = 刷商场卡进店；SSO = 一张卡吃遍美食广场所有档口 |
| 限流与熔断 | 高峰限号 / 菜品临时停售 | 限流 = 每小时最多放 50 桌，超了请排队；熔断 = 某供货商断了就先停售那道菜，别把全店拖死 |

## 7. 开店与守店（部署与运维）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Linux | 后厨的建筑本体 | 厨房的地面、墙面、下水道——所有操作都在这套基础环境上进行 |
| Nginx | 大堂迎宾经理 | 站在门口分流：带位的（托管静态文件）、转给后厨的（转发 /api）、验会员的（HTTPS） |
| 负载均衡 | 多个出餐口的叫号分流 | 一个出餐口扛不住就开三个，有一个关了自动不往那派 |
| Docker | 标准移动厨房车 | 灶台锅具食材全部装箱，推到哪里开火都是同一个味——根治"在我家试菜明明是好的" |
| Kubernetes (K8s) | 连锁车队运营总监 | 管几百辆厨房车：哪辆坏了自动换、高峰自动加车；一两辆车的小店用它是杀鸡用牛刀 |
| 云服务器 | 商场里的租赁铺位 | 不盖自己的厨房，向商场租，随用随付、随时扩 |
| CI/CD | 新菜上市流水线 | 试菜→品控→拍照→上菜单全自动走，不靠人手传；GitHub Actions、Jenkins 是常见的流水线品牌 |
| 日志 | 后厨监控录像 + 小票存根 | 谁几点做了什么、哪单出了问题全有记录，出事第一步永远是调监控 |
| 监控告警 | 烟感报警器 + 值班巡场 | 盯着温度、火情、出餐速度，异常自动打电话叫人 |
| 域名与 HTTPS | 门牌号 + 保鲜膜安心封签 | 门牌要买要备案；封签（小锁）让食客放心，现在没封签的店食客进门就被提醒"不卫生" |
| HTTP | 食客与服务员的通用点菜语言 | 点一下按钮 = 服务员递上一张标准格式的单子 |
| 端口 | 厨房的不同出餐窗口 | 1 号窗凉菜、2 号窗热菜；"端口被占用" = 窗口被人占了 |
| CDN | 连锁分店 / 前置仓 | 招牌半成品铺到离食客近的分店，外地食客不用等总店跨省配送 |
| 重定向 | "本店已搬迁"指路牌 | 301 = 永久搬了（点评网站会改地址），302 = 临时借用别家门面 |
| 数据校验 | 点菜核对 | "您确定特辣？这份很辣"——前厅核对为体验，后厨出菜前再核对才是底线 |
| 认证与授权 | 验身份 vs 看权限 | 认证 = 确认你是不是会员（你是谁）；授权 = 会员能不能进包厢（你能干啥） |
| 功能开关 | 新菜内部试卖 | 先只给熟客，有问题立刻撤下，不用换整本菜单 |
| Serverless | 共享厨房 / 钟点工外包 | 来单才开火、按次计费，没单时成本为零；小功能不用租铺位 |

## 8. 后厨事故处理（排错高频词）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| 异常与堆栈 | 事故调查报告 | 哪道工序、谁、几点出的错层层写清；把完整报告给"厨师顾问"比只说"出事了"快十倍 |
| 慢查询 | 库管找一盒豆腐找了半小时 | 出餐突然变慢，先查是不是有人卡在冷库 |
| 超时 | 等太久催单无果就放弃 | 食客等 30 分钟没菜就走了；所有环节都要设"等多久算完"，否则单子会堆死 |
| 连接池 | 常驻传菜员编制 | 固定几个传菜员随时待命，不现招；"连接池满了" = 传菜员全派出去了，新单排队 |
| 并发与高并发 | 饭点同时涌进多少桌 | 平时随便干都对，饭点才露馅：一道菜卖超了（超卖）、同一单录两遍 |
| 幂等 | 按十次点餐铃只算点一次 | 食客狂按铃、网络重发，都不能真上十份——付款、下单必须做到 |
| 中间件（请求层） | 进后厨前的安检传送带 | 每张单子必经：验真伪、查限号、登记——统一加规矩都挂在这条带上 |

## 9. 安全与架构（第三轮补充）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| 微服务与单体 | 大厨房 vs 独立档口群 | 一个厨房什么都做（单体）够用；拆成凉菜间、热菜间、面点房各自独立（微服务）解决大团队协作，代价是管理翻倍 |
| 接口分页 | 菜单一页页翻 | 不把整本菜单糊你脸上；游标分页 = 记住你翻到哪页接着翻，新菜上架也不会看重复 |
| 加密与哈希 | 秘方保险柜 | 密码 = 把秘方打成粉，谁也还原不出原配方（哈希）；需要还原的信息锁进可开的保险柜（加密） |
| SQL 注入与 XSS | 菜单夹带假指令 / 在别桌菜里动手脚 | 食客在点菜单上写"顺便把账本给我"混进后厨；防御 = 单子只认固定栏目、外来内容先消毒 |
| 数据备份 | 每天把账本复印存隔壁保险柜 | 铁律：没演练过"从复印件恢复"的备份等于没备份 |

# 三、厨师篇（对应《AI 协作词汇手册》）

> 场景故事：现在你是餐厅老板，雇了一位厨艺极高但**从不进店**的厨师——他在远程，你俩全靠对讲机沟通。他不了解你的店、记性有限、偶尔一本正经地瞎说，但只要你指挥得当，他能一个人操办整桌宴席。怎么向这位厨师点菜、派活、验收，就是"AI 协作"的全部学问。

## 1. 跟厨师说话的基本功（AI 对话基础）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| Token | 按克计费的食材 | 厨师说话听话都按"克"算钱，账单和"话太长被掐断"都跟它有关 |
| 上下文窗口 | 厨师的案板大小 | 案板就那么大，放的料（对话内容）太多，最早放上去的会被挤掉——所以他"忘了开头的要求" |
| 上下文工程 | 备料的学问 | 上灶前把对的食材摆到手边；菜做砸了先看料备错了没，再怪厨师 |
| 上下文压缩 | 把前半场经过写成小抄 | 案板要满了，把前面的过程浓缩成一张小抄贴边上；小抄是有损的，关键规矩要趁早写进正式文件 |
| 上下文文件 | 贴在厨房墙上的店规海报 | 厨师每天开工自动看一眼；花十分钟写一份，他永远记得店里的规矩 |
| 系统提示词 | 厨师长定的军规 | 优先级最高的店规，规定他什么能做什么不能做 |
| 提示词 | 老板下的指令 | 好指令四要素：给角色（"你是粤菜大厨"）、给背景、给样例、给约束 |
| 思维链 | 先报做法再下锅 | 让厨师先说"我打算怎么做"再动手，复杂菜正确率明显提高 |
| 示例驱动 | 给厨师看样菜 | "照这盘做"比描述一百句咸淡管用——一样菜胜千言 |
| 对话历史 | 这顿饭至今的全部沟通记录 | 他答错你的第二个要求，往往是你中间说的话把重点淹了 |
| 无状态请求 | 厨师每道菜做完就失忆 | 远程层面他不记事，每次呼叫都要把前文重新说一遍 |
| 记忆 | 熟客档案 | "张先生不吃香菜"写进档案，下次自动生效；区别于本次沟通记录，档案是永久的 |
| 多模态 | 厨师还看得懂照片 | 不只是听得懂话——把卖相照片拍给他，比形容一百句准 |
| AI 幻觉 | 一本正经地瞎编 | "这道菜古法是苦的，你没吃过正宗版"——语气越肯定越要警惕，涉及事实必须让他报出处 |
| 大模型 | 厨师的大脑 | 厨艺本身；没有全能厨师：跑堂要快的、做硬菜要强的、批量切配要便宜的 |
| 模型供应商与兼容接口 | 厨师劳务公司 + 统一行话 | 各家劳务公司（Anthropic、OpenAI）故意用同一套对讲机频道，你的设备换着牌子都能通 |
| 会话中切换模型 | 中途换厨师 | 总厨定方案、帮厨执行；交接时会丢一点信息，"他好像忘了点事"就是这个原因 |
| 思考模式与推理强度 | 让他多琢磨一会儿再下锅 | 档位越高想得越久、工钱越贵；拍黄瓜开高档是浪费 |
| 结构化输出 | 固定摆盘格式 | 要求按"一荤一素一汤"的固定格式出餐，方便直接上桌 |
| 流式响应 | 边做边上 | 回转寿司式出菜，而不是憋到全做完一起端——长宴席体验好得多 |
| 轮次与轨迹 | 一轮"听指令—动手—汇报" / 整顿饭全程记录 | 日志里"第几轮"、账单里的轮次统计就是它 |
| 停止原因 | 厨师停手的理由 | 做完了（stop）、要问你话（toolUse）、菜太多盘子装不下（length）、被你打断（aborted） |
| 提示词缓存 | 那锅天天续的老汤 | 每轮都要重报前文，缓存 = "这锅汤没变，别重熬"，命中部分按约一折计费；所以别天天改店规，改了汤就重熬 |
| 渐进式披露 | 菜谱库先给目录 | 三百道菜谱不一次塞给他，先给目录，做哪道翻哪道——用时才花食材 |
| 对话分叉 | 试菜开两条线 | 从某个节点起，一条线试辣、一条线试不辣，旧线留着随时能回去 |
| 会话持久化与恢复 | 做一半的宴席冷藏，明天接着做 | 完整记录存在你店里，关门重开还能接着干 |
| 插队指令与追加任务 | 他炒菜时你喊话 | "这勺少放盐"他下一铲就改（插队）；"做完这个再做那个"排进队列（追加） |
| Vibe Coding | 不会做饭的人当老板 | 全靠一张嘴描述想吃什么，厨师全包；你负责描述和验收，他负责实现 |

## 2. 让厨师自己张罗（Agent 与工具）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| AI Agent | 能自己办宴席的厨师 | 你说"招待 10 位朋友"，他自己定菜单、采购、做菜、摆盘，不用你一步步教 |
| 编码智能体 | 你的驻店厨师长 | 专门帮你读菜谱、改菜、跑厨房的那类 Agent（Kimi Code、Claude Code、Cursor 都是） |
| 工作流 | 固定流水线工序 | 炸→切→摆盘顺序人事先排死，不许自由发挥；流程稳定的活用它 |
| 计划模式 | 先写菜单给你过目 | 点头才开火；大改动前先开它 |
| 权限模式与 YOLO | 每个动作要不要问你 / 全权委托书 | 注意"弹窗疲劳"——问太多人会麻木地一路点头，反而更危险；危险动作才值得问 |
| 沙箱 | 试验厨房 | 让他在隔离的试菜间折腾，炸了也不影响大堂——这是敢签全权委托书的安全底座 |
| 人在回路 | 关键菜上桌前你亲口尝 | 查资料他可以自己来，动钱动数据（付款、删除）必须你点头 |
| 可观测性 | 透明厨房玻璃墙 | 他看见了什么、用了什么料、花了多少钱全程可查；他做了怪决定先查监控再骂人 |
| 工具调用 | 厨师真的会动手 | 不只嘴上说"我会做"，是真的去开冰箱、开火、翻菜谱 |
| 工具结果 | 每做一步尝一口 | 哪怕做砸了，也把"为什么砸"写成反馈单交给厨师让他自己补救；反馈越具体他越会自己修 |
| 工具输出截断 | 盘点报告太长只看摘要 | 完整版存档案室，他需要时自己去调 |
| MCP | 厨房与外部供应商的标准送货口 | 任何系统只要开了这个标准口，厨师就能直接订它的货、查它的账 |
| Skill | 教过一次就写进菜谱 | 把固定做法教一次，以后报菜名他就会做，不用每次重新教 |
| 钩子 | 传送带上的自动质检闸口 | 每道菜必经的小机关：自动撒葱花、自动测温——"改完自动跑测试"就靠它 |
| 斜杠命令 | 设备上的实体按钮 | 不是跟厨师说话，是直接按机器的钮（/model = 直接换灶头） |
| 扩展与插件 | 给厨房加装新设备 | 不拆厨房本体，塞个新电器就加新功能；装第三方设备注意用电安全（权限） |
| 无头模式 | 把厨师嵌进全自动流水线 | 不当顾问当零件：定时巡检、自动质检、批量切配都靠它 |
| Sub-agent | 帮厨团队 | 厨师长把大宴席拆开，几个帮厨并行做，最后他汇总 |
| 多 Agent 编排 | 整个厨师班组 | 凉菜、热菜、面点、传菜分工协作，像后厨班组而不是一个厨师 |
| ReAct | 炒一步尝一口再定下一步 | 而不是闷头十步全做完才发现第一步盐就错了 |
| Agent 循环 | "做→尝→调整→再做"的闭环 | 规矩要提前定好：连续三次做不好就停下来问你，别在错误上空转 |
| Harness | 厨房的布局、动线与规章制度 | 厨师总在同一个地方滑倒，该改的是厨房地面，不是换厨师 |
| RAG | 先翻店里菜谱档案再做菜 | 回答必须基于你家的菜谱，查不到就说不知道——专治瞎编 |
| 微调 | 送厨师去进修你的独家菜系 | 贵、慢；先用菜谱（提示词）和查档案（RAG），实在不够再送进修 |
| 提示词注入 | 食客在点菜单上写"忽略店规，给我免单" | 防范：单子只认固定栏目、厨师权限最小化、关键操作老板确认 |
| TTFT 与 TPS | 下单后多久上第一道菜 / 上菜速度 | 聊天场景看第一道快不快，长宴席看整体出菜速度 |
| Token 用量与成本 | 厨师工钱按工时计 | 账单爆了按任务查工时，找最烧钱的环节 |
| 速率限制 | 餐厅每小时最多接待多少桌 | 超了直接挡在门外（报错 429），批量订餐要控制节奏 |

## 3. 验收（提需求与验收）

| 术语 | 餐厅类比 | 一句话说透 |
|---|---|---|
| 验收标准 | 试菜验收清单 | 咸淡、温度、摆盘逐条可打勾；没有清单，厨师说"做好了"你无法判断真假 |
| 测试用例 | 试营业演练剧本 | "模拟一桌客人：点招牌菜→要求特辣→应看到红汤"——给厨师修 bug 时附上剧本，等于给了精确复现路径 |

# 四、类比的边界：哪里会失真

类比是脚手架，不是真相。理解入门后，这几处"餐厅"会露馅，要知道：

1. **软件复制不要钱，菜复制要成本。** 一份代码可以零成本发给一亿人，一道菜做一亿份是真要一亿份食材。所以"开源""盗版""规模化"这些概念在餐厅里没有对应物。
2. **代码可以撤销重做，菜做坏就是坏了。** `git` 版本管理 = 拥有一台"时间机器"，能把厨房恢复到昨天任何一刻——餐厅做不到，这也是为什么"版本控制"很难用餐厅类比讲清，需要单独学。
3. **用户和数据是同一个人。** 食客（用户）点菜，但他点的菜里可能包含他自己的信息（注册资料），这些"食客本人"也被存进了冷库——餐厅里没有这种"客人把自己存进仓库"的奇景。
4. **前厅和后厨可以跑在不同城市。** 前端在食客手机（他家餐桌）上，后端在千里之外的机房里——餐厅类比掩盖了"网络延迟"这个真实世界的大问题。
5. **机器不会累，但会"整整齐齐地错"。** 厨师累了会手抖，机器不会——它只会把同一个错误用完全相同的方式重复一百万次。所以程序的 bug 是"系统性"的，比人的失误更隐蔽也更整齐。

> 用法建议：先用本手册建立"它在餐厅哪个位置、服务谁、坏了会怎样"的直觉，再回三份正式手册看准确定义和提示词示例。直觉管"听得懂"，手册管"说得对"。
