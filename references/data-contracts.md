# 数据契约：单据格式、收单检查与接口入口

只在解释 schema、JSON Schema、TypeBox schema、运行时校验、断言、Base64、endpoint，或这些概念的区别时读取。只取当前问题涉及的关系，不把本页整表搬进回答。

## 核心映射

| 技术概念 | 餐厅画面 | 不能丢的技术边界 |
|---|---|---|
| 数据 | 已经填好的实际单据 | 它是具体值，不是规定栏目与约束的 schema |
| schema | 空白单据的栏目设计与收单规矩 | 可描述字段、类型、必填项和约束；数据库、JSON、GraphQL 等语境的 schema 范围不同 |
| TypeScript 类型 | 开工前教员工认单据 | 主要检查代码写法；外部数据到达运行时后，不能只靠静态类型保证内容有效 |
| 运行时校验 | 收单时照规矩检查实单 | 真正检查本次输入；失败后返回错误、拒收还是修正，由应用设计 |
| TypeBox schema | 用 TypeScript 写成、现场仍在的收单规则 | 它是运行时存在的 JSON Schema 规则对象，也可推导静态类型；实际校验仍由兼容验证器或 TypeBox 编译验证能力执行 |
| 测试或运行时断言 | 验菜时卡一条必须成立的条件 | 条件不成立就让测试失败或抛错；一条断言不等于完整 schema 或整套测试 |
| TypeScript 类型断言 | 员工拍胸脯“就按这种单看” | `as` 等写法主要影响静态判断，不会因此检查或转换运行时数据 |
| Base64 | 把货重装成文本通道认得的标准编号箱 | 是二进制到文本的编码，体积通常增加约三分之一；不是加密，也不是压缩 |
| endpoint | 某个办事窗口及其具体事项 | Web API 中常结合方法与 URL 理解，如 `POST /orders`；它是一个访问点，不是整套 API |
| 正则表达式 | 刻好的字样模板 | 拿模板往单据上一卡，格式对不对、号码在哪立刻显形；复杂规则可读性差，适合格式不适合语义 |
| 浮点与 decimal | 破类比直说：数值表示问题，餐厅没有对应 | 浮点是约数记账会丢尾，decimal 是精确到分的记账；金额、利率必须用 decimal，等值比较要留容差 |
| 时区（UTC 与本地时区） | 总店钟与各分店钟 | 账统一按总店钟（UTC）记，给人看再换算成本地钟；跨钟对账先对齐，"今天"在两边可能不是同一天 |

## 五组不能粘在一起的概念

- JSON 是数据写法；schema 决定允许什么结构。
- TypeScript 类型主要在开发期把关；运行时校验检查真正收到的值。
- TypeBox 产出规则；验证器才执行检查。
- 断言检查一个条件；schema 描述一类数据的结构与约束。
- Base64 只换表示方式；endpoint 只定位一次具体交互，二者都不提供认证或授权。
