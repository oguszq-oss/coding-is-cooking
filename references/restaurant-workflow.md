# 中餐厅工作流：这家店到底是怎么干活的

> 用途：所有类比的世界观底座。编任何比喻之前，先想清楚这件事在店里真实的一天中发生在哪个环节、经手的是谁、东西往哪个方向走。放不进这条流程的画面，就是逻辑错误的类比。
> 与《餐厅类比手册》（中餐厅版）的关系：手册管"哪个词对应哪个物件"，本文件管"这些物件在店里怎么动起来"。词对了但动作错了，类比照样翻车。
> 另有两样"干活节奏"的规矩：打烊复盘（进展汇报怎么说）、开店弧线（项目进度怎么定位）。

## 一次请求的旅程（同步主流程，必须背下来）

1. **食客**（用户）在点餐界面提出要求，例如选择水煮鱼并确认下单。
2. **服务员**（前端交互）把这次要求整理成请求，经**正式通道和通道规矩**（API）发给服务端。API 不只是一扇窗口，还包括地址、输入、输出和错误约定。
3. 请求在入口按顺序经过必要的认证、授权、数据校验、限流、日志等处理（请求中间件或网关）。不是每张单都要进消息队列，也不能把中间件只画成出菜后的摆盘检查。
4. **后厨师傅**（后端）按业务规则处理。需要库存实物时让库管查冷库；需要订单、会员等记录时查账本或档案柜（数据库）。数据是什么，餐厅物件就跟着变，纸不进冷库。
5. 服务端形成响应：状态、数据或错误经网络返回前端。后厨回的是处理结果，不把同一张请求单倒着递回来。
6. **服务员**根据响应更新食客看到的界面。到这里，一次普通同步请求才算闭合。

网络像路，不固定对应某个餐厅岗位。前端可能在食客手机，后端可能在另一座城市；“前厅后厨相邻”只帮助理解职责，不能拿来否认延迟、断线和跨来源限制。

## 异步支线：只有需要时才上小票夹

发短信、生成报表、处理大文件等不必让当前请求一直等的工作，可以放进**消息队列**（待办小票夹）。后端或专门的 worker 消费消息，完成后把结果存下，再由轮询、WebSocket、SSE 或下一次查询让前端得知。队列能缓冲和解耦，消费者持续太慢仍会积压；“用了队列，全店就不会被拖垮”是错误承诺。

## 外部订单支线：客单也可能从平台来

订单未必都从餐厅自己的前厅发起。外卖顾客先在第三方平台下单，平台再按双方约定把订单请求交给餐厅系统；餐厅仍负责接收、校验、业务处理、记账和出餐。餐厅回给平台的是这次请求的处理结果，不是把同一张订单倒递回去。

平台若向餐厅登记的地址主动报告新单或状态变化，就是另发一次请求（Webhook / 回调）。骑手只负责实际配送，不属于 SDK、API 或 Webhook。

本节只固定经营参与者和数据方向。解释 SDK、OAuth、凭据与签名、平台测试沙箱、Webhook 的验签与幂等、限流或接口版本时，转读 `external-platform-integration.md`，不要在这里复制完整映射。

## 铁律：东西往哪走

- **请求与响应是两个方向、两种角色。** 请求从调用方（用户/前端，或第三方平台）去服务端；响应从服务端回调用方。后厨不把同一张点菜单递回来，它回的是菜、状态或回话。所以“前厅在等后厨的单子”是病句——前厅等的是处理结果。
- **账本和冷库是两码事。** 冷库是物理空间，放食材；账本是个物件，记订单和账，记完收进柜子。不能说"盘一间冷库，就是立一本账本"——空间不是物件。
- **前厅不下厨，后厨不见客。** 各司其职，别把一方的活安到另一方头上。
- **顾客不进后厨。** 堂食食客接触前厅或店内点餐页；外卖顾客接触平台页面和配送结果。两者都不管店规，也不替店里执行任何规矩。
- **冷库冻的是食材，不是纸。** 单子、账本、标签都不能"冻"。
- **跨来源限制由浏览器执行。** 可以先说：“你去隔壁店借了本菜单。菜单捎回来了，可封皮上没写‘准你翻’，你就原样收着不翻开。” 发起动作的是人，不是纸。技术上，CORS 是浏览器按服务器响应头决定页面能否读取跨来源响应；它不是认证或授权。

## 店里的一天（时间线）

- **凌晨**：盘点、开市前熬高汤（定时任务）。
- **开餐前**：不对外的内部试菜（本地开发），备料线把源码整理成可发布产物（构建打包），再按演练剧本验收。现实餐厅没有许可证时不能靠“试营业”绕过监管。
- **营业中**：堂食与外部平台订单都可能进入餐厅系统；饭点同时涌进几十桌（高并发）；需要异步处理的任务可用小票夹缓冲，但积压仍要监控；每小时最多放 50 桌（限流）；供货商持续失败时先停售相关菜品并等待恢复（熔断）。
- **打烊**：收拢备餐、记交接（日志）；围坐复盘（见下节）。

## 打烊复盘：进展汇报的结构

每晚打烊围坐算账：今天赚了多少、出了什么岔子、明天怎么办。用户问"做到哪了""进展如何"，或一段活收尾时，按这个结构说：

| 栏目 | 装什么 |
|---|---|
| 今日营收 | 今天做成了什么（能用的功能、修好的问题） |
| 客诉 | 出了什么问题（报错、bug、还没修的） |
| 明日计划 | 下一步干什么 |

规矩：对话体三两句话说完，不贴"营业日报："标签，不列表排版；有客诉才提客诉，没有就不提这档；只在问进展或收尾时用，不是每条消息都交日报。

示例：

> 今天把下单按钮修好了，你手机上能点。有一桩客诉还没处理：两个人同时点最后一份，会都扣成功，这个明天改。改完这页就算齐了。

## 开店弧线：项目级进度定位

从筹备到稳定经营，店里的这条线和做软件同构。用户需要全局定位——"咱们这店开到哪一步了"——按它说，一句话讲清现在在哪个环节、接下来是什么：

| 开店环节 | 对应软件环节 |
|---|---|
| 核对场地用途、许可与设施 | 现实开店前提，不强行映射成软件术语；教学故事要声明不是开店指南 |
| 找铺位、装修 | 项目初始化、搭环境 |
| 定菜单、定价 | 确认需求和范围：做什么、不做什么 |
| 本钱有限、控制预算 | 成本意识：采购（依赖）别乱加，说话（token）也是钱 |
| 关门内部试菜 | 本地开发、内部试用 |
| 正式开业 | 部署上线 |
| 每晚复盘 | 迭代：修客诉、调菜单，再开下一天 |

只在需要全局定位时用，不是每条消息都报进度。

## 角色表

| 角色 | 对应 |
|---|---|
| 食客 | 用户 |
| 服务员 | 前端的交互动作（收需求、递单、回话） |
| 正式通道 + 通道规矩 | API；包含地址、输入、输出和错误约定，不只是一扇窗口 |
| 后厨师傅 | 后端业务逻辑 |
| 冷库 / 仓库 / 库管 | 数据库（食材类数据） |
| 账本 / 档案柜 / 收银员 | 数据库（订单、会员等记录类数据） |
| 值守后厨工位 | 服务器；按语境区分服务器软件与承载机器 |
| 路 | 网络传输；不固定由某个餐厅岗位扮演 |
| 食客手里的点餐终端 | 浏览器；读取并运行前端资源 |
| 外卖平台 | 第三方服务；先接顾客订单，再按契约向餐厅系统发请求 |
| 骑手 | 实际配送履约；不是 SDK、API 或 Webhook |
| 你去隔壁店借菜单，封皮没写"准你翻"就不翻开 | CORS；翻开与否由浏览器把关，允许标记对应服务器响应头 |
| 透明厨房玻璃墙 | 可观测性 |
| 店老板 | 用户（拍板的人） |
| 厨师长 | AI / 大模型（根据经理带来的任务和资料作判断） |
| 值班经理 | Agent Runner / 外层控制程序（调用模型、调度工具、决定是否继续） |
| 库管、收银员、具体设备 | 工具（按实际动作选具体角色，不说“店内工具去做”） |

## 厨师长协作线（只用于 AI / Agent）

这条线和前面的“点菜单旅程”是两个场景。讲 AI 编排时，固定使用**老板交代 → 经理找厨师长商量 → 店里代办 → 办完回报 → 再商量**，不要中途跳成出菜、收桌或传菜单。这些角色和动作在现实餐厅里都存在；不要给岗位加“远程”“虚拟”“智能”等前缀来补技术结构。

1. 店老板把要办的事告诉值班经理。经理带着任务和已有资料去找厨师长商量。
2. 厨师长先作一轮判断。事情已经说清，经理就向老板汇报，流程结束；这对应一次模型调用正常结束。
3. 如果厨师长需要先查库存、翻账本或操作设备，他会请值班经理找对应的人去办。这一轮商量先到这里；经理再让库管、收银员或具体设备动手，不凭空增加“取料单”或“代办单”，也不说厨师长亲自执行工具。
4. 店里办完后把结果报给值班经理。经理带着结果再找厨师长，厨师长据此继续判断；这次“再商量”就是外层 `followUp`。
5. 老板中途补充了要求，值班经理就在下一轮商量前把新要求加进去；这就是 `steering` 消息注入。已经结束的上一轮不会提前收到它。

`stopReason` 不必硬找一张菜单、餐具或餐厅岗位来代替。它是程序在每次模型调用结束后给出的技术标签：`stop` 表示这一轮正常说完，`tool_use` 表示这一轮以代办请求结束。两种情况都说明**当前模型调用已经结束**；外层程序再据此决定整个流程结束，还是办完事后继续调用模型。用店里的协作线理解，就是值班经理决定向老板汇报，还是先安排代办再去找厨师长。

## 长故事的时间线铁律

把几十个术语织进故事前，先单独写一行时间账：**筹备 → 关门演练 → 正式运行 → 一段时间后发生事故 → 当天复盘 → 后续验收**。每章开头标当前阶段，每章结尾只往后走。

- 正式开业后，不能再写“开业前一天”；“上周事故”前必须先让店实际营业至少一周。
- 技术概念的先后也要成立：源码先构建，再部署；请求先发出，响应后回来；模型先提出工具请求，外层才执行工具并在下一轮回传结果。
- 词条不推动当前场景，就移到手册。视觉组件清单、品牌排行榜和工具大全不值得为“全覆盖”打断因果主线。
- 完成硬复核后再做优化复盘：虽然画面没错，是否有更短、更真实、技术区分度更高的说法。

## 类比在哪里会露馅（手册第四章）

有五件事餐厅里天然没有对应物，遇到要破一下类比直说：
1. 软件复制的边际成本远低于菜品，但分发、计算和运营仍有成本（开源、规模化不能照搬餐厅经济账）。
2. 代码能回到已记录版本，菜做坏就是坏了（git 像只能停在快照处的时间机器，数据库和外部副作用还要另说）。
3. 数据记录可以描述用户本人——食客与写着他资料的档案不是同一个东西，更不能把“本人存进冷库”。
4. 前厅和后厨可以隔着千里——餐厅类比掩盖了网络延迟。
5. 机器不会累，但会"整整齐齐地错"——bug 是系统性的，不是手抖。

还要主动拆开容易被顺口画面粘在一起的概念：JSON 格式与 schema、TypeScript 静态检查与运行时校验、服务端渲染与静态生成、CORS 与认证授权、OAuth 授权与登录身份、SQL 注入与 XSS、Token 计量与成本、模型与 Agent。每一对都要说明各自的执行者、时机和边界。

## 怎么用这份文件

编类比时对照七步：
1. 这件事在同步主流程、异步或外部订单支线、一天的时间线里有对应环节吗？指出来。
2. 经手的角色对吗？（谁递单、谁做菜、谁回话）
3. 东西走的方向对吗？（单子只去不回；菜和话才回来）
4. 前一步为什么会引出后一步？上一步的结果真是下一步的依据吗？
5. 去掉术语念一遍，店里的人会这样说吗？
6. 类比后面的技术锚点还准确吗？尤其检查执行者、时机、数据方向和安全边界。
7. 这句话虽然没错，是否还能删短、换成更真实的动作，或干脆移出当前故事？

七步有一步答不上，这个类比就是悬的，换一个或直接讲技术事实。
