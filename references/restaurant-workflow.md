# 中餐厅工作流：这家店到底是怎么干活的

> 用途：所有类比的世界观底座。编任何比喻之前，先想清楚这件事在店里真实的一天中发生在哪个环节、经手的是谁、东西往哪个方向走。放不进这条流程的画面，就是逻辑错误的类比。
> 与《餐厅类比手册》（中餐厅版）的关系：手册管"哪个词对应哪个物件"，本文件管"这些物件在店里怎么动起来"。词对了但动作错了，类比照样翻车。

## 一张点菜单的旅程（主流程，必须背下来）

1. **食客**（用户）进门，看装修落座（页面），翻菜单，跟服务员说"一个水煮鱼"（点按钮）。
2. **服务员**（前端交互）把要求写上点菜单，递到**传菜窗口**（API——前厅和后厨之间唯一的官方通道）。
3. **窗口**核单：看会员手牌（JWT）、核对写法（数据校验），合格的单子夹上传菜口的**小票夹**（消息队列）。
4. **后厨师傅**（后端）按顺序从小票夹取单。缺食材去冷库、缺调料去仓库（向数据库取数）。
5. 出菜过**传菜口核对**：对单、测温、摆盘（中间件）。
6. **传菜员**把菜端上桌（响应回到页面）。

外卖多出一段：打包交给**骑手**（网络传输），承诺多久送到（超时机制），超太久食客取消。

## 铁律：东西往哪走

- **单子只往一个方向流：食客/前厅 → 后厨。** 后厨永远不把单子递回来，它回给前厅的是**菜和回话**。所以"前厅在等后厨的单子"是病句——前厅等的是后厨的回话；单子是前厅自己递出去的。
- **账本和冷库是两码事。** 冷库是物理空间，放食材；账本是个物件，记订单和账，记完收进柜子。不能说"盘一间冷库，就是立一本账本"——空间不是物件。
- **前厅不下厨，后厨不见客。** 各司其职，别把一方的活安到另一方头上。
- **食客只接触前厅和外卖盒。** 他不进后厨、不管店规、不替店里执行任何规矩。
- **冷库冻的是食材，不是纸。** 单子、账本、标签都不能"冻"。

## 店里的一天（时间线）

- **凌晨**：盘点、开市前熬高汤（定时任务）。
- **开餐前**：备料流水线把毛菜洗切配成净菜（构建打包）。
- **营业中**：饭点同时涌进几十桌（高并发）；单子靠小票夹削峰，哪个环节慢了不拖垮全店；每小时最多放 50 桌（限流）；供货商断了先停售那道菜（熔断）。
- **打烊**：收拢备餐、记交接（日志）。

## 角色表

| 角色 | 对应 |
|---|---|
| 食客 | 用户 |
| 服务员 | 前端的交互动作（收需求、递单、回话） |
| 传菜窗口 / 传菜员 | API |
| 后厨师傅 | 后端业务逻辑 |
| 冷库 / 仓库 / 库管 | 数据库（食材类数据） |
| 账本 | 订单、会员等记录类数据 |
| 骑手 | 网络传输 |
| 透明厨房玻璃墙 | 可观测性 |
| 店老板 | 用户（拍板的人） |
| 远程厨师 | AI（你是老板，靠对讲机指挥他） |

## 类比在哪里会露馅（手册第四章）

有五件事餐厅里天然没有对应物，遇到要破一下类比直说：
1. 软件复制不要钱，菜复制要成本（开源、规模化讲不了）。
2. 代码能撤销重做，菜做坏就是坏了（git = 时间机器，得单独讲）。
3. 用户本身也是数据——"食客把自己存进冷库"在餐厅里是奇景。
4. 前厅和后厨可以隔着千里——餐厅类比掩盖了网络延迟。
5. 机器不会累，但会"整整齐齐地错"——bug 是系统性的，不是手抖。

## 怎么用这份文件

编类比时对照三步：
1. 这件事在主流程或一天的时间线里有对应环节吗？指出来。
2. 经手的角色对吗？（谁递单、谁做菜、谁回话）
3. 东西走的方向对吗？（单子只去不回；菜和话才回来）

三步有一步答不上，这个类比就是悬的，换一个。
