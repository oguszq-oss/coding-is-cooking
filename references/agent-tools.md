# Agent、工具与评测

大模型对应厨师长，只判断或提出代办；外层程序对应值班经理，检查并调用具体店员或设备，再把结果带回下一轮。全程沿“交代—代办—回报—再商量”走，只用真实岗位与动作，不把模型、Agent 和工具混成一个角色。

## 2. 让厨师自己张罗（Agent 与工具）

| 术语               | 餐厅类比                             | 一句话说透                                                                                                 |
| ------------------ | ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| AI Agent           | 厨师长 + 值班经理 + 店员或设备       | 大模型负责判断和发请求，外层程序负责调用模型、代办、回传；合起来才是 Agent                                 |
| 编码智能体         | 你的驻店厨师长                       | 专门帮你读菜谱、改菜、跑厨房的那类 Agent（Kimi Code、Claude Code、Cursor 都是）                            |
| LLM 抽象层         | 经理统一几家劳务公司的联络方式       | 能统一常见调用，但抹不平模型能力、工具格式、流式事件和错误语义的全部差异                                   |
| 工作流             | 预先编排的工序与分支                 | 由人或系统先定义步骤、条件和错误路径；可包含判断，不等于完全没有分支                                     |
| 计划模式           | 先写方案再决定是否动手               | 是部分产品提供的工作方式；是否必须审批及允许哪些动作以具体系统规则为准                                     |
| 权限模式与 YOLO    | 逐项授权 / 较宽范围自动执行          | 宽权限会放大误删、泄露和外部副作用；授权范围应与风险和可恢复性匹配                                          |
| Agent / 执行沙箱   | 有边界的试验厨房                     | 限制程序可访问的文件、网络和进程等能力；不是第三方平台的非生产测试环境，边界配置不严或另有授权时仍可能影响外部 |
| 人在回路           | 高风险节点由人复核                   | 是否要求确认取决于权限政策；付款、删除、发布等高风险动作通常应设人工关口                                   |
| 可观测性           | 透明厨房与工作记录                   | 记录模型输入、工具调用、耗时、成本、错误和结果；同时要防止秘密与个人数据泄露                               |
| 工具调用           | 厨师长请店里代办                     | 他发出结构化请求；值班经理再让库管、收银员或具体设备动手，不是模型亲自执行。不要另造“取料单”或“代办单” |
| 工具结果           | 办事的人回来报结果                   | 成功、失败和查到的内容先报给值班经理，经理在下一轮商量时告诉厨师长                                         |
| 双层消息模型       | 给老板看的回话 / 给厨师长看的办事记录 | 是部分 Agent 的应用层设计，不是所有模型接口的通用结构                                                       |
| 错误即消息         | 办砸了也照实回报                     | 把失败类型、上下文和可重试信息结构化回传，让外层或下一轮决定如何处理                                       |
| 外层 followUp 循环 | 值班经理带结果再找厨师长             | 厨师长请人代办，店里办完回报，经理带着结果再去商量；如此继续，直到事情说清或必须停下                       |
| 工具输出截断       | 盘点报告太长只带摘要                 | 完整内容是否另存、能否再取由系统决定；摘要要保留错误、关键证据和定位信息                                   |
| MCP                | AI 应用与外部能力的标准接口          | 服务器可暴露 tools、resources、prompts；宿主负责连接、协商、授权与安全边界，模型不会直接任意访问            |
| Skill              | 按需翻阅的岗位手册与资源包           | 在触发时加载说明和资源，不等于永久训练模型，也不保证只报名称就一定正确执行                                  |
| 钩子               | 特定节点自动触发的检查或动作         | 触发时机和能做什么由具体产品决定；并非所有改动都天然经过同一钩子                                           |
| 斜杠命令           | 产品提供的快捷入口                   | 具体语义由产品定义；有些改变会话设置，有些只是插入提示，不能一概说“不是对话”                               |
| 扩展与插件         | 给厨房加装新设备                     | 在主体之外增加能力；安装前核对来源、权限、依赖和数据去向                                                   |
| TUI                | 在文字终端里操作的前台               | 以终端文字界面交互；它与“无头模式”不是同义词                                                              |
| 无头模式           | 不依赖可见前台的后台运行             | 由脚本或服务调用，不等于全自动，也不代表无需权限和人工验收                                                 |
| Sub-agent          | 分工的帮厨                           | 把边界清楚的子任务交给其他 Agent；不一定并行，也要处理共享状态、冲突和汇总                                 |
| 多 Agent 编排      | 整个厨师班组                         | 凉菜、热菜、面点、传菜分工协作，像后厨班组而不是一个厨师                                                   |
| 分支摘要           | 每条试菜线各留交接小结               | 摘要帮助汇总并会丢细节；关键证据仍要能回到原记录                                                           |
| ReAct（Reason + Act） | 先判断一步、请办一步、看回报再判断 | Agent 的推理—行动模式，不是前端 UI 库 React；根据真实结果决定下一步，不一次猜完十步                         |
| Agent 循环         | 交代 → 代办 → 回报 → 再商量          | 循环由外层程序推动；要提前定好次数、预算、超时和失败出口，避免在错误上空转                                 |
| Harness            | 厨房的布局、动线与规章制度           | 厨师总在同一个地方滑倒，该改的是厨房地面，不是换厨师                                                       |
| 事件驱动与发布订阅 | 事件贴上主题后通知订阅岗位           | 生产者与消费者解耦；交付保证、重复、顺序和失败处理仍需另行设计                                             |
| RAG                | 先检索档案再把片段带来商量           | 能补充知识与出处，但不保证检索正确或模型不瞎编；权限、引用与无结果行为仍需设计                              |
| 微调               | 用训练样本调整模型行为               | 主要改变行为或任务表现；RAG 主要补运行时知识，选择取决于问题而非固定的价格顺序                              |
| 提示词注入         | 外来材料夹带“改店规”的话             | 把外部内容当数据、隔离指令与数据、限制工具权限、校验参数，高风险动作前人工确认                             |
| TTFT 与 TPS        | 首句多久到 / 持续说话速度            | TTFT 是首个输出片段延迟；TPS 是持续生成吞吐，Token 口径按供应商定义                                        |
| Token 用量与成本   | 统计传话纸用了多少格                 | 按任务核对输入、输出、缓存与推理相关用量；具体计费口径查供应商合同                                          |
| 速率限制           | 单位时间接待量上限                   | 可按请求或 Token 等口径限制；超限可能返回 429、排队或要求退避，按服务契约处理                               |

## 3. 验收（提需求与验收）

| 术语     | 餐厅类比       | 一句话说透                                                                                      |
| -------- | -------------- | ----------------------------------------------------------------------------------------------- |
| 验收标准 | 试菜验收清单   | 咸淡、温度、摆盘逐条可打勾；没有清单，厨师说"做好了"你无法判断真假                              |
| 测试用例 | 关门演练剧本   | “给定一张订单→执行哪些步骤→应看到什么结果”；有精确输入、动作和预期才便于复现与判断             |
| 测试断言 | 单项验菜条件   | 检查一个预期是否成立；失败就标出本项不合格，不代表其余行为已经验证，类型断言另见 `data-contracts.md` |
| 冒烟测试 | 开门先点火做一单 | 用少量关键检查确认构建或部署没有整体瘫痪；通过后仍不能替代受影响范围的回归测试                  |

解释验收层级时，只展开用户问到的相邻层。未问全量回归条件，就止于“仍需覆盖受影响范围”，不另列触发清单。
