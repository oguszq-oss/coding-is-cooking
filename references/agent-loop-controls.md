# Agent 轮次控制：续谈、换挡与收工

只在解释 `steering`、`followUp`、`prepareNextTurn`、`shouldStopAfterTurn`、`stopReason`、轮次钩子或 Agent 循环停止条件时读取。名字相同，框架的检查点和队列语义也可能不同；项目源码、类型声明和测试高于本表。

## 先分清谁在管

模型只完成本轮回答或提出工具请求。是否再调模型、何时注入消息、是否换模型或停止，由外层 Agent 循环决定；不要写成厨师长自己操纵整个循环。

| 技术概念 | 餐厅画面 | 不能丢的技术边界 |
|---|---|---|
| turn | 厨师长的一轮商量，连本轮代办结果一起结清 | 通常包含一次模型响应及其工具执行与结果，也有框架以一次模型调用为一轮；不等于整项任务 |
| steering | 老板营业中补话，值班经理等这轮说完，再带进下一轮商量 | 消息只影响后续模型上下文，不会改写已完成动作；能否拦住尚未开始的工具按实现判断 |
| prepareNextTurn | 若还要续谈，经理为下一轮换材料、换厨师长，或交代他多想一阵 | 位于当前轮结清后、下一次模型请求前；可返回下一轮的 context、model 或 thinking state，它本身不发起请求 |
| shouldStopAfterTurn | 本轮办完后，经理判断是否到此收工 | 返回 true 表示正常结算当前轮后不再发起下一次模型请求；不会倒过来取消已经完成的工具，且不同于中途 abort |
| followUp | 原本要收尾时，经理又带来后话 | 有的实现指自然结束后排队的追加消息，有的宿主用同名方法继续一次外层调用；先查当前接口 |
| stopReason | 本轮回话为什么停下的技术标签 | 只描述当前模型调用，不自动等于整个 Agent 已结束 |
| abort | 突发情况要求立即停手 | 用于中途取消；能否真正停下底层工具，要看执行者是否处理信号，也不会抹掉已经发生的外部副作用 |

## 在轮次边界怎么读

当前 turn 连同本轮工具及结果先结清。下一次模型请求之前，外层循环要分别回答：有没有新消息要带入，若继续要用什么上下文或模型，以及是否还应继续。`steering`、`prepareNextTurn`、`shouldStopAfterTurn` 各管其中一件事；谁先检查、是否短路，由具体框架决定。除非当前源码和测试已经证明，不写成固定的“先 prepare、再 stop”流程。

遇到 `stopReason=tool_use`，因果线只需写清：模型留下工具请求 → 外层程序检查并调用真实工具 → 结果回到外层循环 → 当前实现决定是否再调模型。

回答只取用户问到的相邻节点。若用户问会不会砍掉工具，就近补出“优雅停止不等于 abort”；除非追问整条循环，不把七个名词全部报一遍。
